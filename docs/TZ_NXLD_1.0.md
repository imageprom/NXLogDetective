# ТЗ: NX Log Detective 1.0

- [ ] Oct 2, 2026 · @Marina

## 1. Цель и принципы

Инструмент получает логи сайта и за одну сессию выдаёт структурированный отчёт по выбранным блокам, файл сигнатур ботов и снимок для следующего сравнения. Методика отрабатывалась на a-spt.ru (12.09–01.10.2026), но это ТЗ шире и подробнее того разбора, поэтому a-spt.ru — тестовый пример, а не эталон.

**Название и версия.** NX Log Detective, версия 1.0. NX всегда пишется заглавными — это фирменный знак. В именах папок, архивов, файлов и репозитория — без пробелов: `NXLogDetective`. Версии по схеме «основная.дополнительная»: сборки до прохождения тестовых прогонов — 0.x, первая утверждённая — 1.0, новые блоки и проверки — 1.1, 1.2…, несовместимые изменения формата сигнатур или снимка — 2.0.

**Краткое имя NXLD** — везде, где полное длинное: файлы результата, формат и коды сигнатур, снимок. В именах файлов нет пробелов, а точки в адресе сайта заменяются на `_` (a-spt.ru → a-spt\_ru).

| Что | Имя |
| --- | --- |
| Репозиторий, папка инструмента | `NXLogDetective` |
| Архив результата | `NXLD_a-spt_ru_2026-09-12_10-01.zip` |
| Excel по блокам | `NXLD_01_Overview.xlsx`, `NXLD_02_Errors.xlsx`, `NXLD_03_Load_Security.xlsx`, `NXLD_04_Bots.xlsx`, `NXLD_05_Marketing.xlsx` |
| Текст для Redmine | `NXLD_Redmine.textile` |
| Снимок | `NXLD_a-spt_ru_2026-09-12_10-01.snapshot.json` |
| Сигнатуры и каталог паттернов | `папка NXLD_a-spt_ru_rules/ (sigma/, eql/, firewall/, ioc/)`, `NXLD_a-spt_ru_patterns.md` |
| Формат сигнатур и коды | `Sigma 2.1.0 / EQL / STIX 2.1, id — UUID v5`, коды вида `NXLD-SPAM-001` |

**Кто пользуется.** Аналитики (обзор и раздача задач), рекламщики (маркетинг и ошибки), программисты и глубокие аналитики (ошибки, безопасность, боты, сигнатуры). Роли не выбираются: человек отмечает нужные блоки галочками.

**Принципы**

- **Без состояния.** Всё нужное приходит на вход, всё полученное уходит на выход. Папки проекта и памяти между сессиями нет.
- **Код измеряет, ИИ расследует.** Всё, что можно посчитать, считает код: результат воспроизводим. ИИ решает, что применимо, ищет странное, проверяет догадки и пишет находки.
- **Любой сайт.** Нет заранее заданных форм, карточек или разделов. Сайт может быть на CMS, фреймворке или голом HTML. Устройство сайта определяется из лога. Неприменимое явно помечается («форм не обнаружено — раздел пропущен»), а не придумывается.
- **Базовые термины:** «раздел» и «элемент каталога». Конкретное название (квартира, товар, услуга, статья) ИИ выбирает по сайту.
- **Без адресатов.** Кому передать проблему, решает человек. Результат только структурированный и внятный.
- **Лучше продублировать, чем забыть.** Каждый блок самодостаточен. Проблема, важная для двух блоков, есть в обоих, в формулировке своего блока.
- **Персональные данные маскируются** в отчётах (`+7 9** ***-**-12`).
- **Интернет — по минимуму**, только для уточнения выводов из лога (раздел 14).

**Структура проблемы (находки).** Блок · важность (срочно / важно / к сведению) · что происходит, одной фразой · факты (цифры, даты, URL, IP) · где править (конфиг nginx или `.htaccess`, код, содержимое, robots.txt, рекламный кабинет, фид, настройки защиты, сервер) · что сделать · статус (только при сравнении) · устойчивый ключ для сравнения.

## 2. Вход и анкета

Обязателен только лог. Всё остальное необязательно и только уточняет результат.

| Вход | Обязательно | Зачем |
| --- | --- | --- |
| Access-логи (любые части, `.gz`/`.zip`, любой порядок) | Да | Основа анализа |
| Error-логи | Нет | Серверная часть, причины ошибок, сбои базы, правила защиты |
| Файлы сигнатур (0..N, с других проектов или один общий) | Нет | Проверка по известным ботам, объединение |
| Снимок прошлой проверки, старые логи или старые отчёты | Для сравнения | База «было». Если прошлый анализ сделан в этом же чате, не нужна |
| Список подозрительных IP | Нет | Разбор каждого адреса и связей |
| Названия кампаний | Нет | В метках обычно только номера |

**Анкета**

- **Блоки:** ☑ Общий анализ (всегда) · ☑ Ошибки (всегда) · ☐ Нагрузка и безопасность · ☐ Боты · ☐ Маркетинг
- **Действие:** ◉ Полная проверка · ○ Сравнение (база из этого чата, снимка, старых логов или отчётов)
- **Сигнатуры:** ☐ Проверить по загруженным · ☐ Выгрузить: сигнатуры (Sigma YAML, Sigma JSON, EQL) · правила защиты (nginx, fail2ban, ModSecurity, Яндекс SWS, AWS WAF, Cloudflare) · индикаторы (STIX 2.1, список IP, CSV) — по форматам галочками
- **Дополнительно:** список IP, названия кампаний

Если анкета без ответа, берётся «Полная проверка» по всем блокам. Если пришли сигнатуры, проверка по ним включается сама.

Отдельной выгрузки IP как формата нет (лист больше 10 000 строк продолжается в CSV той же структуры — решения 7 октября; это не выгрузка). IP лежат на листе «IP», в тексте (если их до 10–15), а важные — в выгрузке индикаторов (раздел 10).

## 3. Разведка

Разведка идёт первой всегда и отвечает на два вопроса: что именно анализируем и как устроен сайт. Результат — листы «О данных» и «Карта сайта». Карта коротко показывается человеку, но ждать ответа не обязательно.

### 3.1. Что на входе (первый экран отчёта)

- Список файлов и тип каждого: access или error.
- **Какие сайты в логах:** по имени файла, по полю хоста, по `server:`/`host:` в error-логе nginx, по рефереру. Несколько сайтов разбираются отдельно.
- По каждому сайту и файлу: период, число строк, объём, пропуски по времени, дубли на стыках.
- **Можно ли анализировать.** Если все запросы с 127.0.0.1 или с адресов CDN, настоящих IP нет: это первая находка, анализ ботов и IP ограничен.

### 3.2. Формат строк

Какой формат, каких полей нет (реферер, UA, размер, время ответа) и что из-за этого не посчитать.

### 3.3. Серверная часть

Нужна, чтобы понимать, какие конфиги править.

| Что | Откуда видно | Надёжность |
| --- | --- | --- |
| nginx или Apache | Формат error-лога; код 499 только у nginx | Надёжно |
| Связка nginx → Apache / PHP-FPM | `upstream: http://127.0.0.1:8888`, `fastcgi://unix:/run/php/php8.1-fpm.sock` | Надёжно, часто с версией PHP |
| Язык бэкенда | `.php`, `.aspx`, `.jsp`, `/static/admin/`, `/_next/`, `PHP Fatal error` | Надёжно при ответах 200 |
| Пути на сервере | `/home/bitrix/www`, `/var/www/html`, `C:\…` в error-логе | Косвенно указывают на ОС |
| ОС | Только косвенно | Догадка, так и помечаем |
| Версии nginx/PHP | В логах обычно нет; заголовки `Server`, `X-Powered-By` при доступе в интернет | По ситуации |
| Протокол | HTTP/1.1 или HTTP/2 в строке запроса | Надёжно |

### 3.4. Статика или движок

Движок определяется по путям, которые **отдают 200 настоящим браузерам**, а не по запросам сканеров.

| Движок | Характерные пути |
| --- | --- |
| 1С-Битрикс | `/bitrix/`, `/local/`, `/upload/iblock/` |
| WordPress | `/wp-content/`, `/wp-includes/`, `/wp-json/` |
| Joomla | `/components/com_*`, `/media/jui/`, `index.php?option=com_` |
| UMI.CMS | `/images/cms/`, `/udata/`, `/emarket/` |
| Drupal | `/sites/default/files/`, `/core/misc/` |
| MODX | `/assets/components/`, `/connectors/`, `/manager/` |
| OpenCart | `index.php?route=`, `/catalog/view/theme/` |
| Webasyst / Shop-Script | `/wa-data/`, `/wa-apps/` |
| NetCat, HostCMS, DLE | `/netcat/`, `/hostcmsfiles/`, `/engine/` |
| Tilda, конструкторы | Страницы без своей статики, ресурсы с чужого CDN |
| Фреймворки | Laravel, Django, Next.js, Nuxt |
| Голый HTML | `.html` без серверного кода |
| Свой движок | Ни одного из признаков |

Список пополняется. Признаки двух движков с ответом 200 — находка (остатки старого сайта или поддомен).

### 3.5. Устройство сайта

- **Что считать страницей:** HTML-ответ, после которого браузер грузит ресурсы. Статика — по расширению. AJAX — запросы сразу после страницы с ней в реферере.
- **Шаблоны URL:** числа и ID заменяются звёздочкой. Шаблон с множеством ID — элементы каталога. Параметры списков — фильтры.
- **Разделы и элементы каталога** ИИ называет по сайту.

### 3.6. Цели и спрос

- **POST-цели:** куда люди отправляют данные со страниц. Признак успеха — по реакции сервера (редирект на `?success`, страница «спасибо», 302 вместо 200).
- **GET-цели:** страницы «спасибо», скачивания, переходы через `/go?url=`.
- **Спрос на лендингах:** по запросам, которые порождают кнопки блоков (форма с параметром `form=X`, `?tariff=…`, AJAX, скрытые поля в GET). Кнопки без запросов к серверу не видны: так и пишем, рекомендуем цели в Метрике.
- **Формы, подгружаемые на каждой странице** (как `form.php?view=modal` на a-spt.ru): шаг «открыл форму» для них не считается.
- **Рекламные метки** находятся автоматически.

### 3.7. Отправки данных через GET

Запросы с `name=`, `phone=`, `tel=`, `email=`, `fio=`, `message=` пишутся на отдельный лист и разбираются на три случая:

- настоящая форма через GET: данные людей в логах и в реферере для третьих сайтов, «Важно»;
- попытки взлома через параметры → безопасность;
- спам через GET → боты.

### 3.8. Служебные файлы и свои

robots.txt, sitemap, фиды, favicon; адрес админки по движку; сотрудники (вход в админку), мониторинги (один адрес по расписанию), тестовые отправки. Свои исключаются из статистики людей.

## 4. Очистка визитов и группы трафика

Визиты сначала чистятся, потом считаются. Визит — запросы одного IP + UA с паузами не больше 30 минут. Время на сайте по логу — нижняя граница (последний запрос минус первый).

| Искажение | Как выглядит | Что сбивает | Что делаем |
| --- | --- | --- | --- |
| Двойная загрузка в браузерах приложений | Та же страница дважды за секунды, первая иногда без статики | Глубина, отказы, ложные «боты» | Повторы адреса за N секунд = один просмотр |
| Редиректы | 301 → 200 на один переход | Двойной просмотр | Редирект и цель — один просмотр |
| Формы и блоки на каждой странице | `form.php?view=modal` в каждом визите | «Открытие формы», глубина | Часть страницы, не действие |
| AJAX, пагинация, фильтры | Много запросов к одному разделу | Глубина | Отдельно от просмотров |
| Рекламная проверка перед кликом | Робот системы за секунды до человека | Ложные визиты без статики | Узнаём по сети и UA, исключаем |
| Возврат и восстановление вкладок | Страница снова через часы | Лишние визиты | Пауза 30 минут |
| Несколько людей за одним IP | Разные UA, параллельные запросы | Один «визит» из нескольких | Визит по IP + UA |
| Смена IP посреди визита | Реферер со страницы, открытой с другого IP | Один человек = два визита | Склеиваем по рефереру и UA |

В «О данных» показываем, сколько склеено и исключено каждым правилом. Новое искажение на конкретном сайте ИИ описывает и добавляет в правила.

**Группы трафика**

| Группа | Подгруппа | Что это |
| --- | --- | --- |
| Люди | — | Браузерный UA, подгрузка ресурсов, человеческий темп |
| Роботы (называют себя) | известные | Поисковики, SEO, ИИ, мониторинги, превью, рекламные, фиды. Проверяются по сети |
|  | неизвестные | `bot`, `crawler`, `spider`, `curl`, `python-requests`, `Go-http-client` в UA; кто это, выясняет ИИ |
| Боты (не называют себя) | явные, «тупые» | Пустой или древний UA, без статики, HEAD, странные пути |
|  | маскирующиеся | Видны только по поведению, сигнатуры |
| Свои | — | Сотрудники, мониторинги, тесты |

В «Общем анализе» группы только считаются, разбор — в «Ботах».

## 5. Блок «Общий анализ» (всегда)

Общая картина сайта и входная точка для аналитика: что анализируем, ключевые цифры, срочное по всем блокам со ссылками на подробности.

1. **Кто приходит:** группы трафика (раздел 4) — визиты, IP, запросы, доля трафика в ГБ.
2. **Динамика по дням** для людей и ботов, провалы и всплески со ссылкой на «Ошибки».
3. **Откуда люди**, верхний уровень: реклама, поиск, Карты, соцсети и мессенджеры, ИИ-ассистенты, ссылки, прямые.
4. **Поведение:** устройства, часы и дни недели, страны, страницы входа, популярные разделы, глубина, отказы, время (после очистки).
5. **Спрос** (если есть каталог или блоки): самые просматриваемые элементы, фильтры, поиск по сайту.
6. **Конверсии в общем виде** (если есть формы или цели): сколько отправок и принято; от людей, ботов, тестов; потерянные заявки; общая конверсия визит → заявка; динамика по дням; одна строка по каналам. Воронки и разрезы — в «Маркетинге».
7. **Нейропоиск.** Люди из ИИ-ассистентов: рефереры `chatgpt.com`, `perplexity.ai`, `copilot.microsoft.com`, `gemini.google.com`, `chat.deepseek.com`, `giga.chat`, `claude.ai`, метка `utm_source=chatgpt.com`, Алиса и Нейро (проверить на логах). ИИ-роботы по назначению: обучение, поисковый индекс, запрос пользователя (ChatGPT-User, Perplexity-User, Claude-User — живой человек спросил ассистента про сайт); правила robots.txt для них.

**Листы `NXLD_01_Overview.xlsx`, по порядку:** «О данных» → «Сводка» → «Главное» → «Карта сайта» → «По дням» → «Люди и боты» → «Каналы» → «Разделы» → «Спрос» → «Конверсии» → «GET-отправки» → «IP».

**Лист «Главное»:**

- сверху счётчик по блокам: срочно / важно / к сведению / где подробно (невыбранные блоки — «не анализировалось»);
- ниже только срочное, сгруппированное по блокам: что происходит, главная цифра, файл и лист с подробностями;
- при сравнении — «новые / сохраняются / исправлены» по блокам.

## 6. Блок «Ошибки» (всегда)

Разделяем ошибки, которые видят **люди, поисковики и реклама** (находки), и ошибки ботов и сканеров (одна строка «шум»).

1. **Общая картина:** коды по дням и часам, отдельно для людей, поисковиков и ботов. Главная цифра — доля ошибок у людей.
2. **Сбои:** пик (в минуту ≥ 3 страниц с 5xx у ≥ 3 разных IP и ≥ 25% страниц с 5xx; один робот на битых адресах — не сбой) и окно деградации вокруг него (доля 5xx + 499 у страниц втрое выше обычной для этого часа и не меньше 20%, или запросов меньше 30% обычного); в отчёте «деградация X–Y, пик A–B». Пик ≥ 2 мин — Срочно; деградация без пика ≥ 10 мин и ≥ 20 ошибок — Важно; 502 / 503 / 504; 499 (не дождались) по URL; медленные страницы, если есть время ответа.
3. **Отвалилась база данных:** статика 200, а страницы в ту же минуту 500 / 502 / 503; все страницы одного размера (заглушка, иногда с кодом 200); цепочка «растут 499 → 502/504»; частичный сбой каталога; в error-логе `Too many connections`, `MySQL server has gone away`, `SQLSTATE`, `DB query error`. Уверенность — по числу совпавших признаков.
4. **Error-лог по типам:** таймауты и падения бэкенда, PHP Fatal / Warning / Deprecated с файлом и строкой, 413, `limiting requests`, `No such file`, `Permission denied`, `No space left on device`, `worker_connections`, SSL. По каждому: сколько, первая и последняя дата, примеры. Без error-лога пишем, чего не видно.
5. **5xx по шаблонам:** с какого дня, постоянно или плавает, сколько людей задето, какие входы.
6. **404 по источнику:** битые ссылки на сайте (со страницей-источником); ресурсы, которые запрашивает каждая страница; входы из поиска, рекламы, Карт, соцсетей; поисковые роботы; сканеры (шум). Вариации адреса, которые должны редиректить: слэш, регистр, `index.php`, двойной слэш, кириллица.
7. **Мягкие ошибки:** 200 с подозрительно малым размером; soft 404 (разные мусорные URL с одинаковым ответом); страница «похудела» с какого-то дня.
8. **Битые файлы и типы:** файл 200 весом 0 байт; `.jpg` или `.css` с размером HTML-страницы; меняющийся размер; обрывы загрузки; 416; `upstream sent invalid header`, `zero size buf`.
9. **Редиректы** (косвенно): цепочки, циклы, 302 вместо 301, редирект на 404.
10. **Служебные файлы:** robots.txt, sitemap, фиды, favicon, manifest, `.well-known` — статус и размер по дням, кто забирает и не перестали ли.
11. **Что видят поисковики:** доля 5xx и 404 у подтверждённых Яндекса и Google по разделам.
12. **Реклама и цели** (всегда, даже без «Маркетинга»): посадочные с метками с ошибками; рекламные фиды; отправки форм, получившие ошибку (потерянные заявки); AJAX форм и блоков.
13. **Изменения во времени:** детектор выкладок — URL, у которых в какой-то день сменился статус (как `/action/*`: 500 с 24.09, 404 с 30.09).
14. **Защита, которая блокирует не тех** — находки здесь, механизмы — в разделе 7. Кого режут: людей, подтверждённых поисковиков, робота проверки объявлений Директа, роботов фидов, платёжные и CRM-уведомления, рекламные клики с `yclid`/`gclid`. По какому признаку: сеть или страна, браузер (встроенные браузеры приложений), адрес, частота, день начала. Страницы-заглушки одного размера, петли проверки. Защита перед сайтом не пускает заблокированных в лог: видны только провалы, нужны логи защиты.

**Коды ответа** смотрим отдельно для людей и поисковиков и для ботов:

| Код | Проблема, если | Норма, если |
| --- | --- | --- |
| 400 (часто слишком большие cookie) | У людей | У ботов |
| 401 | Закрыт рабочий раздел | Тестовый сайт, служебное |
| 403 | Люди, поисковики, отправки форм | Сканеры |
| 405 | POST формы на непринимающий адрес | Боты |
| 408 | Массово у людей | Единично |
| 410 | Удалено по ошибке | Удалено намеренно |
| 413 / 414 / 416 | Загрузки в формах, длинные URL фильтров, битые файлы | Атаки |
| 429 | Режет людей или поисковики | Режет парсеры |
| 444 | Попали люди | Боты |
| 495–497 | Конфиг SSL | — |
| 499 | Медленные страницы | Единично |
| 500 / 502 / 503 / 504, 520–527 (Cloudflare) | Всегда | — |

Не ошибки, но показываем: 304 (кэш), 206 (докачка), доля 301 и 302.

**Важность.** Срочно: сайт был недоступен; 5xx на страницах с людьми; ошибки на рекламных посадочных; сломан фид; формы не принимают; защита режет людей, поисковики, рекламу или платежи; закончился диск. Важно: битые ссылки, 404 на входах из поиска и Карт, отсутствующие ресурсы, медленные страницы, soft 404, цепочки редиректов, ошибки у поисковиков. К сведению: Deprecated, 404 ботов одной строкой.

**Листы NXLD\_`02_Errors.xlsx`:** «Проблемы» (одна строка = одна проблема, сгруппированная по причине; страницы-источники, дающие больше всего битых ссылок, первыми) → «Сводка» → «О данных» → «Ошибки по дням» → «Проблема × день» (тепловая карта) → «Сбои» → «5xx по шаблонам» → «404: входы извне» → «Битые ссылки» → «Отсутствующие ресурсы» → «Служебные файлы» → «Error-лог» → «Изменения статусов» → «Защита: кого блокирует» → «Карта редиректов» (старый адрес → предлагаемый новый, каждую строку проверить глазами).

Столбцы «Проблем»: проблема · где (шаблон или файл) · пример адреса · с какого и по какой день · кого задело (людей, поисковиков, рекламных кликов, заявок) · откуда приходят · место правки · что сделать · важность.

## 7. Блок «Нагрузка и безопасность»

Здесь — последствия и угрозы; «кто это» — в «Ботах». Если «Боты» не выбраны, здесь всё равно есть главные IP и сети нападающих. Лог показывает признаки, а не доказательства взлома.

### 7.1. Нагрузка

1. **Объём:** запросы и ГБ по дням и часам, максимум запросов в минуту, доля каждой группы.
2. **Пики:** кто их создал и **приводит ли нагрузка к сбоям** (499 и 5xx в те же минуты).
3. **Дорогие запросы:** кто больше всех запрашивает страницы, а не статику; ловушки для роботов (комбинации фильтров и сортировок); частые AJAX; медленные адреса.
4. **Грузит, но ничего не даёт:** SEO-сервисы, частые мониторинги, ИИ-краулеры обучения, обход поисковиками мусорных адресов (на a-spt.ru: Semrush 105 тыс. запросов, Prufen 3,1 ГБ).
5. **Вес сайта:** трафик по типам файлов, самые тяжёлые файлы, тяжёлые картинки, видео напрямую, кэш (доля 304, повторные скачивания), хотлинк.

### 7.2. Безопасность

1. **Админка:** кто заходит (IP, сеть, страна), успешные входы и попытки, входы из нетипичных сетей, открыта ли всему миру, подбор паролей.
2. **Открытые служебные файлы:** отдал ли сервер 200 на `.env`, `.git/`, бэкапы, `phpinfo`, `restore.php`, `bitrixsetup.php`, `adminer.php`, phpMyAdmin, логи, листинги папок, тестовые копии. 404 — фон, 200 — срочно.
3. **Сканеры:** что искали (по цели), откуда, что получили.
4. **Атаки через параметры** (SQL-инъекции, XSS, `../`, `${jndi:`, команды) в адресе, UA и реферере. 404/403 — отбито; 200 с необычным размером или 500 — возможно, нащупали уязвимое место.
5. **Уязвимости движка:** известные уязвимые адреса для определённого движка (список в данных инструмента). Существует и отвечает — срочно.
6. **Признаки веб-шелла:** исполняемый файл в папке загрузок, случайное имя, появился в какой-то день, его вызывают несколько IP в основном POST-запросами, ответ 200.
7. **Утечки через адреса:** персональные данные в GET, токены и сессии в URL (`sessid=`, `token=`, `key=`).
8. **Флуд:** шквал с IP или подсети, привёл ли к ошибкам, сработала ли защита.

### 7.3. Защита: механизмы и работает ли она

| Слой | Признаки |
| --- | --- |
| Защита перед сайтом (Cloudflare, DDoS-Guard, Qrator, StormWall, ServicePipe) | IP из сетей защиты; `/cdn-cgi/…`, `/.well-known/ddos-guard/…`, `/__qrator/…`; проверочные редиректы |
| nginx | 503/429 от ограничения частоты, 403 по IP или стране, 444, проверка cookie; `limiting requests`, `access forbidden by rule` |
| mod\_security хостинга | 403/406 на слова в параметрах, номер правила в error-логе |
| Защита CMS | Своя страница блокировки, часто 200 и одинаковый размер |
| fail2ban, файрвол | IP внезапно пропадает посреди визита (слабый признак) |
| Капча | Редиректы на страницу проверки |

Работает ли защита: какая доля вредных запросов получила 403 / 404 / 444, а какая 200; не на грани ли лимиты. Ложные блокировки людей, поисковиков и рекламы — находки в «Ошибках» (раздел 6, пункт 14).

**Важность.** Срочно: признаки веб-шелла; служебный файл или бэкап отдан с 200; атака получила 500 или нетипичный 200; вход в админку из нетипичной сети; нагрузка вызывает сбои. Важно: админка открыта миру; подбор паролей; токены или персональные данные в URL; защита не останавливает атаки; тяжёлые бесполезные роботы; ловушки; не работает кэш; огромные картинки; хотлинк. К сведению: фон сканеров с 404.

**Листы `NXLD_03_Load_Security.xlsx`:** «Проблемы» → «Сводка» → «О данных» → «Нагрузка по часам» → «Пики» → «Кто нагружает» → «Ловушки для роботов» → «Типы файлов» → «Тяжёлые файлы» → «Админка» → «Служебные файлы: что отдано» → «Сканеры: что искали» → «Атаки в параметрах» → «Подозрительные файлы» → «Защита».

Если нет поля размера — нет трафика и веса. За CDN видна часть нагрузки. На голом HTML нет админки и инъекций по существу, остальное проверяется.

## 8. Блок «Боты»

Подробный разбор групп, которые в общем анализе только посчитаны, плюс операторы, сети и сигнатуры.

1. **Объявленные роботы** по категориям: поисковики, SEO, ИИ (обучение / поиск / запрос пользователя), мониторинги, превью, рекламные, фиды, архивы, библиотеки, неизвестные. По семейству: запросы, IP, дни, сети и страны, что смотрел, коды, трафик, соблюдает ли robots.txt. Подлинность по ASN (Google 15169, Yandex 13238, Microsoft 8075, Apple 714 и др.). Неопознанные роботы и мониторинги не гадаем и не останавливаемся: помечаем «не опознан — на усмотрение оптимизатора» с объёмом, нагрузкой и тем, что они смотрят (как Prufen на a-spt.ru: 34 тыс. запросов, 3,1 ГБ).
2. **Явные боты:** пустой или древний UA, только HEAD, нет статики, странные пути; группировка по UA и сети.
3. **Маскирующиеся боты по классам** (неприменимые классы пропускаются):

| Класс | Главные признаки |
| --- | --- |
| Парсер | Много страниц и элементов каталога, нет статики и AJAX, ровный темп, без реферера |
| Спам форм | Вход на битый URL → главная → форма через 20–40 с; форма без просмотра; пачки; ротация UA; удалённые обработчики; спам через GET |
| Разведка | Короткие визиты с хостингов и VPN перед атакой, редкие общие URL |
| Накрутка кликов | Рекламные клики без статики, из дата-центров, с мгновенным уходом; осторожно с мобильными операторами |
| Headless | HeadlessChrome, Puppeteer, Lighthouse |
| Ротаторы | Один оператор, много IP и UA |
| Подделки роботов | UA поисковика из чужой сети |
| Сканеры | Кратко, подробно — в разделе 7 |

4. **Операторы:** связываем IP по уликам трёх сил. Сильная (достаточно одной): смена IP посреди визита (визит пришёл со страницы, которую за ≤ 2 ч до этого открыл другой IP и получил 404); общий битый вход, куда люди напрямую почти не заходят (≤ 5 IP). Средняя: общий битый вход, куда заходят и люди; реферер — битый адрес, через который входил другой спамер; тот же приём входа (прямой заход на несуществующий адрес одного раздела, затем форма). Слабая (сама не связывает): тот же UA целиком, та же сеть (ASN), одна волна (отправки в один день с разницей ≤ 2 ч). Группы склеиваются по сильной улике или по средней плюс любой другой. Лист «Операторы: улики»: IP A — IP B — сила — улика — доказательство — учтена ли (связи, которых не хватило для склейки, тоже показываются). Смена IP у человека (страницу за ≤ 30 мин до отправки открыл другой IP с тем же UA в обычном визите) — не спам. Результат: «Оператор 1: N IP, сети, волны, что делал, сколько заявок прошло» с доказательствами связей.
5. **Сети ботов** по ASN и типу, с пометкой, что делать с адресом: хостинги и облака — можно банить подсетью; VPN-релеи и домашние провайдеры — только по поведению; мобильные операторы — не банить; зарубежные — по аудитории сайта.
6. **Проверка присланного списка IP:** что делал и когда, сеть, класс, связи; нет в логе — так и пишем.
7. **Сигнатуры** — раздел 10.
8. **Чем боты мешают:** принятые бот-заявки, доля ботов в рекламном трафике, нагрузка, искажение Метрики (предупреждение).

**ИИ-роботы и нейропоиск — отдельный разрез** (лист «ИИ-роботы»). В общем анализе и маркетинге нейропоиск — это люди, пришедшие из ассистентов; здесь — сами роботы:

- **по назначению:** обучение (GPTBot, ClaudeBot, CCBot, Bytespider, meta-externalagent), поисковый индекс (OAI-SearchBot, PerplexityBot, Claude-SearchBot, YandexAdditional), запрос пользователя (ChatGPT-User, Perplexity-User, Claude-User);
- **что читают:** разделы и элементы каталога, коды ответа (не отдаём ли им ошибки и блокировки);
- **спрос через ИИ:** какие страницы забирают роботы «по запросу пользователя», по дням, и сколько людей потом пришло из ассистентов;
- **правила:** что разрешает robots.txt и соблюдают ли;
- **подлинность:** по сети владельца; чужая сеть — подделка;
- **нагрузка:** запросы и трафик каждого;
- **что сделать:** по каждой группе вариант «разрешить / ограничить / запретить» с последствиями (запрет поисковых и пользовательских ИИ-роботов убирает сайт из ответов ассистентов).

**Важность.** Срочно: бот-заявки принимаются; оператор активен сейчас; подделки или накрутка в оплачиваемом трафике. Важно: массовые парсеры; тяжёлые неизвестные роботы; роботы, игнорирующие robots.txt; совпадения с операторами из других проектов. К сведению: общий фон.

**Листы NXLD\_`04_Bots.xlsx`:** «Проблемы» → «Сводка» → «О данных» → «Роботы: семейства» → «Роботы: сети» → «Подделки» → «Явные боты» → «Боты: классы» → «Операторы» → «Операторы: улики» → «Бот-сети» → «Проверка IP» → «ИИ-роботы» → «Сигнатуры: описание» → «Сигнатуры: срабатывания» → «Сигнатуры: проверка» → «IP».

## 9. Блок «Маркетинг»

Откуда приходят люди и что приводит к заявкам. Блок работает и без рекламы; рекламные разрезы добавляются, если реклама есть. Денег в логе нет, и NXLD их не считает: анализируются только логи, без выгрузки расходов.

### 9.1. Всегда (даже без рекламы)

1. **Каналы подробно:** поиск (Яндекс, Google, остальные; запросов в реферере нет), Карты (Яндекс, 2ГИС, Google), площадки и агрегаторы, соцсети и мессенджеры, рассылки, ИИ-ассистенты, ссылки с других сайтов, прямые (всегда завышены, оговариваем).
2. **Воронка по каждой форме:** визиты людей → открыли форму (если грузится по клику) → отправили → принято → из принятых от людей.
3. **Конверсия по всем каналам** и разрезы: страницы входа, разделы, элементы каталога, блоки лендинга, устройства, часы и дни, новые и повторные, визиты и время до заявки, первый и последний канал (по IP, с оговоркой).
4. **Качество трафика** по каналам: доля ботов, недогруженные страницы, мгновенный уход, глубина, время, элементы каталога, конверсия.
5. **Очистка визитов по каналам и площадкам:** сколько склеено и исключено; предупреждение у метрик, где очистка заметно меняет цифры (особенно приложения РСЯ).
6. **Органика:** входы из поиска по страницам и дням; что обходят роботы и куда приходят люди.

### 9.2. Если есть реклама

1. **Метки находятся сами:** `utm_*`, `yclid`, `gclid`, `gbraid`, `fbclid`, `rb_clickid`, `_openstat`, `from`, `calltouch_tm`, `roistat` и любые повторяющиеся параметры на входах. Шаблоны с макросами разбираются: кампания, группа, объявление, фраза, площадка, тип площадки, позиция, регион, устройство.
2. **Проблемы с метками:** неподставленный макрос (`{campaign_id}`), `yclid` без UTM, разная разметка, метки, ломающие адрес.
3. **Рекламные системы:** Яндекс Директ, Google Ads, VK Реклама, Telegram Ads, Авито и другие.
4. **Тип площадки:** поиск; РСЯ сайты; РСЯ сторонние приложения; приложения Яндекса; Карты и геореклама; сервисы Яндекса.
5. **Разрезы:** кампании, группы, объявления, фразы, регионы, устройства, часы, позиции, конкретные площадки (`source`).
6. **«Площадки к отключению»:** готовый список для кабинета — заметный объём, плохое качество, ноль конверсий, с признаками.
7. **Накрутка:** бот-клики, повторные клики, клики из дата-центров, ночные всплески.
8. **Посадочные:** ошибки и блокировки, медленные, мобильные и десктоп, реклама на главную вместо раздела, ответы роботам модерации (YandexDirect, AdsBot-Google).
9. **Рекламные фиды:** статус, размер, кто и как часто забирает.
10. **Изменения во времени:** первый и последний клик кампаний и площадок.

**Важность.** Срочно: клики на ошибки или блокировки; сломан фид; ошибки у роботов модерации; массовые бот-клики. Важно: площадки и кампании с объёмом и нулём конверсий (на a-spt.ru: кампания 714750845, 17 тыс. визитов, 0 заявок); сломанные метки; реклама на главную. К сведению: распределения.

**Листы NXLD\_`05_Marketing.xlsx`:** «Проблемы» → «Сводка» → «О данных» → общие данные («По дням», «Каналы», «Разделы», «Спрос», «Конверсии») → «Воронки» → «Конверсии: разрезы» → «Качество трафика» → «Очистка по каналам» → «Органика» → рекламные листы («Реклама: системы и типы площадок», «Кампании», «Объявления», «Фразы», «Площадки», «Площадки к отключению», «Регионы», «Устройства», «Часы», «Посадочные», «Метки: проблемы»).

**Контрольная точка и «до и после» не нужны** (решение 2 октября 2026). NXLD анализирует лог как есть; сравнение по времени правки было экспериментом под один случай. Сравнение с прошлой проверкой по снимку остаётся. В коде 0.1 пока есть (параметр `--control-point`, лист «До и после», черновые проблемы, раздел в `brief.json`, строки в скиле) — убрать при ближайшей правке маркетинга.

## 10. Сигнатуры, правила защиты и индикаторы

Утверждено 02.10.2026. Только промышленные форматы с открытой документацией, никаких своих гибридных полей. Паттерны **строятся из данных конкретного проекта** (готовые классы — только стартовые гипотезы): подтверждённые боты → общие шаги, паузы, цели, UA, сети → пороги по распределению → проверка на логах (пойманы боты, не задеты люди с заявками) → ужесточение и повторная проверка.

Два разных действия:

- **Экспорт и импорт** — полный пакет STIX 2.1 без потерь, только штатные объекты и значения (раздел 10.5). Только это называется экспортом; импорт восстанавливает всё.
- **Выгрузка правил** — неполные односторонние форматы для конкретных систем (таблица ниже, разделы 10.1–10.3), строятся из той же модели. Чужие файлы таких форматов — не импорт, а «проверка логов по чужим правилам» (раздел 10.4).

| Раздел | Задача | Кто читает | Форматы 1.0 |
| --- | --- | --- | --- |
| Сигнатуры поведения | Описать, как выглядит бот, чтобы найти его в логах | Аналитик, SIEM | Sigma YAML, Sigma JSON, EQL |
| Правила защиты | Блокировать или ограничивать | Админ, файрвол, сервер | nginx, fail2ban, ModSecurity/Coraza, Яндекс Smart Web Security, AWS WAF, Cloudflare |
| Индикаторы и списки | Обмен адресами и шаблонами между системами и проектами | TI-платформа, анти-DDoS | STIX 2.1, текстовый список IP, CSV |

Позже, по запросу: YARA-L 2.0 (Google SecOps), конвертеры в MaxPatrol SIEM и KUMA по примерам правил заказчика. Отдельные генераторы Splunk SPL и KQL не делаем: их получают из Sigma через pySigma.

### 10.1. Сигнатуры поведения

| Формат | Что в файле | Проверка при выгрузке |
| --- | --- | --- |
| Sigma 2.1.0, YAML | N базовых правил (по одному на шаг) + 1 правило корреляции. Для трёх шагов — 4 файла; опционально один файл через `---` | Официальные JSON Schema Sigma + `sigma-cli` |
| Sigma 2.1.0, JSON | Те же документы одним JSON-массивом, каждый элемент проходит официальную JSON Schema Sigma. Читается `json.loads()` / `JSON.parse()` | Официальные JSON Schema Sigma |
| EQL (Elastic) | Одна строка: `sequence by source.ip with maxspan=… [web where …] [web where …]` | Разбор Python-пакетом `eql` |

Правила:

- **Порядок шагов** в Sigma — корреляция `temporal_ordered` (не `temporal`, который допускает любой порядок); окно — `timespan`, группировка — `group-by`.
- **Поля:** Sigma — таксономия `logsource: category: webserver` (`c-ip`, `cs-method`, `cs-uri-stem`, `cs-uri-query`, `sc-status`, `cs-referer`, `cs-user-agent`, `sc-bytes`, `cs-host`); EQL — ECS (`source.ip`, `url.path`, `url.query`, `http.request.method`, `http.response.status_code`, `http.request.referrer`, `user_agent.original`), категория `web`.
- **UUID** правил — v5 от названия паттерна: повторная выгрузка даёт тот же `id`, в системах заказчика правило обновляется, а не задваивается. Корреляция ссылается на базовые правила по `name`.
- **Только то, что формат умеет.** Счётчики (например, 3+ разных UA за сутки) — отдельной корреляцией `value_count`/`event_count` в Sigma; в EQL их нет. «Между шагами не было события» — `![…]` в EQL; в Sigma этого нет. Чего формат не умеет (число страниц между шагами, смена IP посреди визита), пишется словами в `description` и `falsepositives`.
- **Человеческое описание** у каждого паттерна: как выглядит, пример реального визита, чем отличается от человека, когда ошибается. Оно в `description` правил, в каталоге паттернов `NXLD_…_patterns.md`, на листе «Сигнатуры: описание» и в тексте Redmine.

### 10.2. Правила защиты

Это не сигнатуры, а меры, выведенные из найденного: файрволы проверяют запросы по одному и последовательностей не понимают.

| Формат | Что выгружаем | Ограничения |
| --- | --- | --- |
| nginx | deny-список (только хостинги), `map` по UA и путям сканеров, `limit_req` на формы | — |
| fail2ban | Фильтр и jail: N ответов 404 за M секунд, пути сканеров, частые POST на формы | Работает по тому же access-логу |
| ModSecurity / Coraza (SecRule) | Пути сканеров, поддельные роботы; упрощённая последовательность на коллекции IP: «404 на входе → POST на форму за N минут → блок» | Только при установленном модуле |
| Яндекс Smart Web Security | Правила профиля безопасности (YAML для CLI / Terraform): IP-списки, URI, метод, заголовки, категория бота; ARL на формы | Свои правила в формате ModSecurity туда не загружаются |
| AWS WAF (WAFv2 JSON) | IP set, rate-based (от 10 запросов, окна 60–600 с) на POST к формам, пути сканеров, UA | Нет последовательностей и кодов ответа; в РФ — для проектов вне российского контура |
| Cloudflare (Rulesets API JSON) | Custom rules (пути, UA + сеть для поддельных роботов), rate limiting, в т. ч. по числу 404 (`http.response.code`), IP-список | Последовательности (`cf.sequence.*`) — только шаблоном для Enterprise с Fraud Detection |

### 10.3. Индикаторы и списки

- **STIX 2.1:** индикаторы с IP операторов и сканеров и шаблоном поведения (`FOLLOWEDBY … WITHIN`), для TI-платформ заказчика и обмена между проектами.
- **Текстовый список IP и CSV** (адрес, сеть, ASN, тип сети, первая и последняя активность, причина): для анти-DDoS-сервисов (Qrator, DDoS-Guard, StormWall и др.) и ручной загрузки.
- Правило отбора IP прежнее: операторы, сканеры, поддельные роботы, разведка; хостинги — к блокировке, домашние и мобильные сети — только метка.

### 10.4. Загрузка чужих файлов

Формат определяется по содержимому: YAML с `detection` или `correlation` — Sigma; JSON-массив документов Sigma — Sigma JSON; строка `sequence …` или `… where …` — EQL; JSON с `Statement`/`Action` — AWS WAF; JSON с `expression`/`action` — Cloudflare; STIX bundle — STIX. Sigma и EQL прогоняются по логам (свой исполнитель для подмножества Sigma; для EQL — пакет `eql`, диалект проверить на практике). Правила защиты и индикаторы только читаются: IP-списки и пути сверяются с логом. В отчёте — что сработало, что найдено только загруженными правилами, что только нашим анализом, и не задеты ли люди с конверсиями.

### 10.5. Полный пакет STIX 2.1

| Что передаём | Объект STIX 2.1 |
| --- | --- |
| Поведенческое правило | `indicator`, `pattern_type: sigma` (полный YAML правила) и `pattern_type: stix` (`FOLLOWEDBY … WITHIN`) |
| IP-адреса и сети | `ipv4-addr`, `autonomous-system` |
| Связь «IP ↔ поведение» и «IP ↔ IP» | `relationship` с описанием улики |
| Что и сколько раз видели | `sighting` (число, первая и последняя дата) |
| Оператор | `intrusion-set` со связями на IP и паттерны |
| Статус и уверенность | `indicator_types`, `confidence` (0–100), `revoked`, `valid_from`/`valid_until`, `opinion` с причиной |
| Источники знания | `external_references` (база, идентификатор, дата) |
| Автор и распространение | `identity` «NX Log Detective <версия>», TLP 2.0: AMBER — правила проекта и индикаторы, GREEN — универсальные правила |

EQL в пакет не входит (его нет в штатном словаре) — только выгрузка. При загрузке пакета три проверки, все в отчёте: только поведение (новые IP), только адреса (известные IP), вместе (высокая уверенность; известный IP с человеческим поведением — повод проверить).

### 10.6. Статусы адресов

| Статус | В STIX | Когда ставится | Действие |
| --- | --- | --- | --- |
| Чёрный список (blocklist) | `malicious-activity`, высокая уверенность | Подтверждённый паттерн с хостинга; участник оператора с сильной уликой; подделка робота; Spamhaus DROP | Блокировать |
| Кандидат (watchlist) | `anomalous-activity` | Слабая или одна улика; есть в публичных списках, но здесь чист; плохое поведение с домашнего или мобильного адреса | Наблюдать, решить вручную |
| Анонимайзер / общий адрес | `anonymization` (VPN, Tor, WARP, Private Relay); мобильные сети и общий хостинг — `unknown` с пояснением | По публичным спискам анонимайзеров и типу сети | Только по поведению, не банить по IP |
| Белый список (allowlist) | `benign` | Официальные списки роботов (Google, Bing, Apple, OpenAI, Perplexity; Яндекс — ASN 13238 + обратный DNS); сотрудники; мониторинги; платёжные и CRM-уведомления; узкие ручные исключения (IP + адрес) | Не трогать |
| Отклонён (false positive) | `revoked: true` + `opinion` с причиной | Кандидат оказался своим | Хранится, чтобы не добавили снова |
| Истёк | прошёл `valid_until` | Срок действия вышел (домашние адреса — короткий срок) | Пересмотреть |

### 10.7. Мировые базы (без регистраций и ключей)

Только источники без ключей и регистрации: снимки лежат в `data/` с датой и работают без интернета; при наличии интернета обновляются автоматически, дата пишется в отчёт. Лицензию каждого источника проверяем перед включением.

| Назначение | Источники |
| --- | --- |
| Известное хорошее | Официальные JSON-списки роботов (Google, Bing, Apple, OpenAI, Perplexity), MISP warninglists, диапазоны CDN (Cloudflare) |
| Известное плохое и анонимайзеры | Spamhaus DROP, FireHOL level1, blocklist.de, IPsum, выходные узлы Tor, VPN-сети из warninglists, Stop Forum Spam (скачиваемые списки, если лицензия позволяет) |
| Опознание ботов по UA | nginx-ultimate-bad-bot-blocker, crawler-user-agents, Matomo device-detector, ai.robots.txt, Matomo referrer-spam-list |
| Опубликованные правила и инструменты | SigmaHQ (web), OWASP CRS, Nuclei templates, Emerging Threats Open |

Применение: опознание инструмента или бота по имени; дополнительная улика для IP с источником и датой (в пакете — `external_references`); ссылка на опубликованное правило вместо дубля. Отсутствие в базах — не алиби (операторы через домашние прокси туда обычно не попадают); запись для домашнего IP может устареть — учитывается дата. Платные и требующие ключа сервисы (GreyNoise, AbuseIPDB, данные Касперского и Positive Technologies) не используем.

## 11. Сравнение и снимок

Сравнение — тот же анализ нового периода плюс сопоставление с прошлым. Старый период не пересчитывается.

**Откуда берётся прошлое**

| Что есть | Что делаем |
| --- | --- |
| Прошлый анализ в этом же чате | Из контекста и рабочих файлов |
| Снимок прошлой проверки | Из снимка (или со скрытого листа `NXLD_01_Overview.xlsx`) |
| Старые логи | Прогон только выбранных блоков = база |
| Только старые отчёты (Excel, Redmine) | ИИ восстанавливает базу частично, остальное — «нет базы» |

**Что сравниваем**

1. **Изменения на сайте** по двум картам: разделы, шаблоны, формы и обработчики, движок и сервер, robots.txt и sitemap, метки и кампании, защита.
2. **Цифры «было → стало»** в пересчёте на день, по возможности те же дни недели; заметные изменения подсвечиваются, мало данных — так и пишем.
3. **Статус каждой проблемы** по устойчивому ключу (блок + тип + объект):

| Статус | Когда |
| --- | --- |
| Новая | Не было в прошлый раз |
| Сохраняется | Есть сейчас; помечаем «лучше» или «хуже» по главной цифре |
| Исправлена | Только при доказательстве: адрес отвечает 200, форма принимает, фид отдаётся |
| Нет данных | Адрес никто не запрашивал. Это не «исправлена»; при доступе в интернет перепроверяем |
| Не анализировалось | Блок не выбирали |

4. **Боты:** новые операторы и IP, вернувшиеся адреса, продолжает ли оператор, какие сигнатуры начали или перестали срабатывать.
5. **Маркетинг:** появившиеся и исчезнувшие кампании и площадки; выполнены ли рекомендации (площадки «к отключению» перестали давать клики).
6. **Пересечение периодов:** если новый лог содержит старый период, сравниваем только новую часть и предупреждаем.

**Как показывается:** в файлах блоков — столбец «Статус» в «Проблемах», исправленные отдельным блоком внизу, лист «Было → стало»; в общем файле — счётчик статусов в «Главном» и лист «Что изменилось на сайте»; в Redmine — блок «С прошлой проверки (дата)».

**Снимок** — один небольшой файл, например `NXLD_a-spt_ru_2026-09-12_10-01.snapshot.json`:

- внутри: сайт, период, версия инструмента, карта сайта, ключевые цифры по блокам и дням, проблемы с ключами и цифрами, IP и операторы, сработавшие сигнатуры;
- объём — десятки, редко сотни килобайт (иначе `.gz`);
- хранится вложением в задаче Redmine; копия — на скрытом листе `NXLD_01_Overview.xlsx`;
- сырых данных нет: для новых метрик будет «нет базы».

После проверки достаточно хранить снимок и файл сигнатур (если выгружали). Остальное — для людей.

**Правила файлов блоков**

- В «Проблемах» только проблемы этого блока, по важности. Проблема двух блоков есть в обоих, с формулировкой своего блока (404 на посадочной: в «Ошибках» — «адрес отдаёт 404, вот откуда ведут»; в «Маркетинге» — «кампания X льёт клики на 404»).
- Одна строка — одна проблема, сгруппированная по причине, а не по адресу.
- Подробные листы — все данные полностью; на них ссылаются строки «Проблем».
- Лист «IP»: адрес, сеть, страна, категория, сигнатуры, первая и последняя активность, действие (бан, проверка, наблюдение).

**Текст для Redmine**

Связный читаемый отчёт, который не наскучит начальству. Эталон стиля — три текста ручного анализа a-spt.ru (итоги ботной активности, связи IP, анализ полного лога): они лежат в скиле как образцы тона, не как шаблон.

**Автор и голос.** Работу делает Детектив: «Детектив изучил логи…», «Детектив провёл расследование и связал…», «Детективу не удалось определить…». Рекомендации безличные: «рекомендуется», «следует», «нужно отключить». Методика безлично: «принятой считается отправка…». Никаких «мы рекомендуем» и адресатов. Правило действует везде, где есть связный текст.

**Стиль.**

- Один абзац — одна мысль, обычно 1–3 предложения. Разные темы не смешиваются: технологии сайта, люди, заявки, оговорки — отдельными абзацами; факт, его объяснение и вывод по сути — тоже можно разделить.
- У разделов говорящие заголовки-выводы: «Фальшивые заявки — основная проблема», а не «Боты».
- Цифра со смыслом там, где нужен вывод: из скольких, какая доля, с какого числа, продолжается ли. Где достаточно цифр — просто цифры, без комментариев.
- Сравнение вместо голой цифры; таблица — только для сравнения; хронология — для историй (волны атаки, сбой).
- Объекты названы точно: формы — по-человечески и с адресом, кампании — с номером и названием, тип объекта без обобщений («сторонние мобильные приложения РСЯ», а не «площадки»).
- Короткое «как считали» там, где от этого зависит доверие; честные оговорки и отрицательные выводы; попутные выводы.
- Простой язык: «арендованный сервер», «косая черта»; коды ответа — с расшифровкой. Числа: «10,8 млн», «14 500», «1,6 ТБ»; дни — диапазоном, без длинных перечней.
- Ссылка на файл — как приглашение для более глубокого понимания: «Все 254 отправки форм с источником и результатом — на листе «…» в NXLD\_05\_Marketing.xlsx», а не «→ лист X».

**Структура.**

1. Заголовок: «NX Log Detective: сайт, период».
2. Вступление — один абзац и тип проверки. Первичная: «Детектив провёл первичное исследование логов сайта … за …: N дней, N строк…». Повторная: «Детектив провёл повторное исследование: логи за … сравнены с проверкой за …». Здесь же что проверялось и оговорки по данным (пропуски, обрыв, нет error-лога).
3. «Что Детектив узнал о сайте» — короткий портрет: на чём сделан, сколько людей и заявок, откуда приходят, доля роботов и ботов. Слишком техническое остаётся в Excel.
4. «Главное» — 3–5 выводов по одной фразе.
5. При повторной проверке — «Что изменилось с прошлой проверки»: исправлено, сохраняется, новое.
6. Тематические разделы — пронумерованы, порядок задаёт вред, а не блок. Мелкое в текст не попадает: в конце раздела одна фраза «Ещё N мелких — на листе «Проблемы» в …».
7. «Рекомендации» — нумерованный список по приоритету, у каждого пункта ссылка на раздел и ожидаемый эффект. Метка «срочно» — только у немногих пунктов, остальное не маркируется: приоритет виден по порядку.
8. «Оговорки и открытые вопросы»: чего не видно в логах, что подтвердить позже, неопознанные роботы (на усмотрение оптимизатора).
9. «Файлы» — по строке на файл: что в нём и с какого листа начать.

Точные IP и адреса — в тексте, если их до 10–15, иначе «N адресов, список на листе …». Объём: вступление, «Главное» и рекомендации читаются за 2–3 минуты; полная проверка — примерно как третий образец.

**Важность проблем (для порядка разделов, «Проблем» и Excel).** Для читателя градации называются «Приоритетные · Важные · Остальные», в данных остаются Срочно / Важно / К сведению. Важность — не жёсткий порог, а взвешивание факторов:

1. **Кого задело** — визиты людей, а не запросы.
2. **Намерение канала** — входы с Карт, из Поиска, Рекламы и всё, что касается заявок, «горячие»: для них порог мелочи (0,1% визитов) не действует, минимум «Важные».
3. **Видимость** — видит ли человек проблему. Иконки и картинки оформления (CSS, спрайты, svg в шаблоне) важны по объёму; заглушки ленивой загрузки и файлы, которые запрашивают только роботы, — «Остальные».
4. **Длится ли сейчас** — продолжается на конец лога / повторяется / была один раз и прошла / давняя (давняя понижается на ступень).
5. **Деньги** — задевает ли заявки и рекламу.

**Сбои:** сайт не отвечает в конце лога и не восстановился — «Приоритетные», первой карточкой («сайт, возможно, лежит прямо сейчас»); сбои повторяются (несколько за период или в одно время — похоже на расписание) — «Важные»; долгий единичный сбой (от часа) или сбой, задевший заявки и рекламу, — «Важные»; короткий единичный сбой, после которого сайт работает, — «Остальные» с пометкой «возможно, перезагрузка или плановые работы, уточнить у хостинга».

**Служебные разделы и формы входа.** Форму входа узнаём по поведению, а не по названию раздела. **Отпечаток формы** — типичный размер ответа посторонним без POST (с разбросом в несколько процентов: токен, дата). Неудачный вход — после POST ответ того же размера, что отпечаток. Успешный вход — после POST ответ заметно другой: переадресация (301/302/303) **или** 200 другого размера, дальше тот же адрес получает ответы раздела, непохожие на отпечаток. Подбор пароля — много POST с разных адресов, все ответы совпадают с отпечатком (отдельная проблема). POST нет совсем — по логу ничего не утверждаем: «Служебный раздел отвечает посторонним — проверить, что там», вопрос для Детектива; при наличии интернета он открывает адрес и смотрит, есть ли поле пароля. Форма подтверждена — проблема только в индексации: «Страница входа видна поисковикам», закрыть в robots.txt, «Остальные». «Открыт без пароля» — только когда внутренние страницы раздела отдаются тем, кто не входил. Ограничение: если кабинет после входа почти того же размера, что форма, лог их не различит — решает проверка страницы.

**Гибкость:** пороги (0,1%, час, «конец лога», «повторяется») лежат в файле правил `data/severity_rules.json` и правятся без кода. Детектив может поднять или опустить важность с объяснением (`edits.json`). Причина важности выводится в карточке строкой «Обстоятельства» — что подняло или опустило проблему («вход из Карт — горячий канал», «сбой пришёлся на рекламные визиты», «короткий единичный сбой»); строка есть, только когда обстоятельства есть.

**Тексты:** у ошибок всегда указывается код ответа (404, 499, 500…) и, где можно, вид атаки (SQL-инъекция, XSS, перебор путей): «SQL-инъекция в параметре фильтра arrFilter\_22\_MIN: 3 запроса, ответ 500». Смысл кода поясняется только там, где без него непонятно (499 — человек не дождался ответа). В «Из показаний» у отсутствующих файлов — визиты людей, а не запросы.

Одна причина — одна проблема (однотипное сводится, повторы между блоками склеиваются). Самопроверка: если «Приоритетных» больше 5 или «Важных» больше 10–12, ИИ пересматривает оценки.

**Кто пишет.** Движок итоговый текст не пишет. Он готовит материал в `brief.json` (раздел 15.1): по каждому разделу цифры уже с контекстом, сравнения, хронологии, точные названия объектов, ссылки на листы; при повторной проверке — и расхождения со снимком. ИИ пишет текст по этому материалу и своим находкам из расследования, не читая логи и Excel; недостающий факт добирает готовой командой расследования. Перед выдачей: каждая цифра сверена с материалом, ничего не придумано, персональные данные маскированы, «срочно» не больше чем у 3–5 пунктов. Расход — ориентир +15–30 тыс. токенов на проверку, это принято. Если ИИ недоступен, движок собирает запасной черновик с пометкой «черновик».

**Состав `brief.json`** (ориентир 20–40 КБ, числа уже округлены и с контекстом, у каждого факта — файл и лист):

1. **Проверка:** сайт, период и число дней, строки access и error, выбранные блоки, тип (первичная / повторная с периодом прошлой), оговорки по данным (пропуски, обрыв, нет error-лога).
2. **Портрет сайта:** движок и сервер; люди, роботы, боты, свои; каналы с долями и заявками; формы с человеческими названиями; что считается принятой заявкой; заявки людей, ботов и тестов.
3. **Проблемы** — сгруппированные, с важностью по вреду, фактами, датами начала и конца, признаком «продолжается на конец периода».
4. **Материал по блокам:** боты (операторы с волнами, сетями, сценарием и типами улик, одиночки, подделки, ИИ-роботы); маркетинг (типы площадок с «визитов на заявку», кампании без заявок, площадки к отключению, встроенные браузеры); ошибки (сбои, 5xx по разделам со сменой статусов, реклама на ошибках с последним кликом, битые входы, фиды, отсутствующие файлы, error-лог); безопасность (сканеры, отданное с указанием, кто получил — свой или чужой, открытые разделы, админка); нагрузка (трафик по типам, тяжёлые файлы, кэш, тяжёлые роботы, мониторинги с интервалом, ловушки).
5. **Файлы и листы** для ссылок; **открытые вопросы** (неопознанные мониторинги и роботы, непринятые отправки людей).

Порядок: `analyze` пишет `brief.json` → ИИ расследует и пишет `work/NXLD_Redmine.textile` по правилам и образцам из скила → `report` кладёт его в архив; если текста нет — запасной черновик движка с пометкой «черновик». Образцы стиля в скиле: три текста ручного анализа и принятый текст a-spt.ru от 2 октября. Проверка качества: независимый агент с одним скилом и brief.json пишет текст, цифры сверяются с материалом.

**Итоговое сообщение в чате:** текст для Redmine блоком кода и список вопросов к человеку.

**Обсудим отдельно, когда дойдём до отчётов:** структура Overview и перестройка его данных; говорящие заголовки листов и таблиц в Excel (практика принята, форма — нет); лист о том, что делают люди (что считается заявкой, полезные действия, типичные сценарии); воронка; нужен ли связный текст ещё и в Excel.

## 13. Порядок работы и большие логи

Лог читается целиком один раз, дальше вся работа идёт на компактных таблицах. Повторные вопросы («что делал этот IP?») не требуют нового прохода.

**Для человека**

1. Загружает логи и дополнительные файлы.
2. Отвечает на анкету (без ответа — полная проверка по всем блокам).
3. Видит «Что на входе» и карту сайта, может поправить (ждать не обязательно).
4. Следит за прогрессом в списке задач.
5. Получает файлы, короткое сообщение о срочном и вопросы, которые ИИ не решил сам. Работа из-за вопросов не останавливается.

**Внутри**

| Шаг | Кто | Что делается |
| --- | --- | --- |
| 1. Приём | Код | Распаковка, типы файлов, сайты, период, порядок, дубли, пересечения, пропуски |
| 2. Разведка | Код → ИИ | Код собирает кандидатов, ИИ составляет карту сайта |
| 3. Основной проход | Код | Один проход: сети и страны, роботы, очистка, визиты, агрегаты блоков, сигнатуры → компактные таблицы |
| 4. Расследование | ИИ | Читает таблицы, ищет странное, проверяет догадки точечно, интернет по правилам, пишет проблемы |
| 5. Сигнатуры | Код + ИИ | Кандидаты → проверка на логе → файл и каталог |
| 6. Сравнение | Код + ИИ | Снимок или контекст против текущего |
| 7. Сборка | Код | Excel по блокам, Redmine, снимок, сигнатуры |
| 8. Самопроверка | Код + ИИ | Цифры сходятся, ссылки на листы живые, у проблем есть факты, данные людей замаскированы, неприменимое помечено |

**Большие логи.** Выборкой не пользуемся: для ботов и заявок важна каждая строка. Память не растёт с размером лога: визиты закрываются по ходу.

- **Claude:** 10 млн строк — 5–10 минут. Узкое место — передача файлов; в инструкции — части до 50 МБ. При привязке чата к компьютеру файлы забираются партиями.
- **ChatGPT:** ограничены размер файла и время запуска. Основной проход — кусками с сохранением прогресса (человек пишет «продолжи»). Очень большой лог — инструмент скажет, как разбить.

**Несколько сайтов в логе:** каждый отдельно, со своими файлами и снимком. Много сайтов — вопрос, какие разбирать; без ответа — все, начиная с самого посещаемого.

## 15. Экономия ресурсов

Токены тратятся на то, что ИИ читает и пишет; диск и память — на работу движка. Ограничения вводятся только вместе с проверкой, что результат не стал хуже (15.4).

### 15.1. Токены

1. **ИИ не читает сырые данные.** Логи, большие таблицы и Excel читает только движок. Для ИИ он выдаёт выжимку `brief.json` ограниченного размера (ориентир 20–30 КБ): карта сайта, ключевые цифры, черновые проблемы, топ странного по блокам.
2. **Тихий движок.** В чат — только прогресс и итог в несколько строк; предупреждения и подробности — в `run.log`.
3. **Готовые команды расследования** вместо кода, который ИИ пишет каждый раз: `ip`, `visit`, `url`, `sheet --top N`. Вывод каждой команды ограничен по числу строк.
4. **Скилл читается по частям.** `SKILL.md` — короткое ядро; справки по форматам выгрузки, STIX, мировым базам — отдельными файлами, открываются только когда нужны.
5. **Таблицы собирает код, связный текст пишет ИИ по brief.json.** Excel, снимок, пакет STIX, правила собирает движок. ИИ пишет текст для Redmine (раздел 12, ориентир +15–30 тыс. токенов), `edits.json` и итоговое сообщение. В чат по умолчанию — срочное и вопросы; полный текст Redmine — по просьбе или файлом.
6. **Рамки расследования.** Сначала «Срочно» и аномалии; лимит уточняющих запросов (ориентир 10–15 на проверку); если ответ не меняет вывод — не копать; ничего не перечитывать и не рендерить Excel для просмотра.
7. **Внешние данные (мировые базы, раздел 10.7) обрабатывает только движок.** Обновление — своей командой, не веб-инструментами ИИ; только если снимку больше недели или по просьбе; ИИ видит только итог (совпадения по кандидатам и чёрному списку и сводку).
8. **Один сайт — один чат.** Длинная история тянется за каждым сообщением.

### 15.2. Диск

Замер 0.1 на a-spt.ru (10,8 млн строк): логи на входе \~1,1 ГБ сжатых (\~5 ГБ в распакованном виде), рабочая папка 2,1 ГБ, результат \~2 МБ.

| Требование | Как |
| --- | --- |
| Логи не распаковываются | Движок читает `.gz` и `.zip` напрямую |
| Рабочая папка — ориентир не больше \~1 ГБ на 10 млн строк | Удалять куски разбора после сборки общей таблицы (сейчас 0,56 ГБ); убрать лишние справочники из таблицы GET-отправок (сейчас 117 МБ); хранить общую таблицу со сжатием (сейчас 1,2 ГБ) |
| Снимки мировых баз | Десятки МБ в `data/` |
| Очистка | После выдачи результата рабочая папка может быть удалена; для сравнения нужен только снимок |

### 15.3. Память и время

- Claude: полная таблица запросов в памяти допустима; пиковая память и время каждого этапа замеряются и пишутся в «О данных». Замер 0.1 — предстоит (время: разбор \~2 мин, блоки и отчёты \~1 мин).
- ChatGPT: точные лимиты среды не опубликованы — проверить на практике. Известно: файл до 512 МБ. Нужен режим обработки кусками с сохранением промежуточных итогов без полной таблицы в памяти и продолжением после обрыва.

### 15.4. Проверка «не стало хуже»

Любая оптимизация и любое ограничение принимается, только если на контрольных данных результат не ухудшился:

- **Контрольные данные:** логи a-spt.ru за 12.09–01.10.2026, однодневный кусок без error-лога, искусственный сайт на голом HTML; далее — каждый новый проект.
- **Сравнение с эталонным прогоном предыдущей версии:** число запросов и визитов по группам, принятые заявки людей и ботов, поддельные роботы, сбои, список проблем по ключам и важности, ключевые листы. Любое расхождение либо объясняется (улучшение), либо исправляется.
- **Ресурсы:** диск, пиковая память, время и расход токенов по этапам (разведка, расчёт, расследование, выдача) замеряются до и после.
- **Порядок изменений кода:** перед правкой сверить текущую версию с последней проверенной; каждая версия фиксируется (репозиторий git), чтобы изменения были видны и откатываемы.

**Лист «Анатомия сайта» (решение 3 октября).** В Overview сразу после «Проблем», вместо листов «Карта сайта». Карточки в стиле индекса, строки второго уровня с отступом. Показывается только то, что реально существует: страницы, которые отдавались людям с ответом 200 (адреса сканеров вроде /.git/ не попадают). Блоки:

1. **Админка и закрытые зоны** — адрес админки движка (переносится из «Технологий» обзора), служебные разделы с формой входа, личный кабинет, тестовые копии.
2. **Каталоги** — по карточке на каждый. Два вида: **каталог (дерево)** — уровни вложенности строками второго уровня, шаблоны адресов, элементы (сколько адресов открывали люди), фильтры; **лента (плоский список)** — список и материалы (новости, статьи, акции, отзывы). Уровень называется по слову из адреса (словарь частых: flat, product, news, blog, reviews…) или Детективом; если понять нельзя — «Уровень N». Статистика — ссылкой на листы разделов и шаблонов.
3. **Простые разделы** (без вложенности) — с визитами и пометками «форма», «кабинет», «вход».
4. **Формы и конверсии** — что это по имени обработчика, где появляется, признак успеха, отправлено и принято; отдельно — «не цели» по группам.
5. **Папки движка** — известные для опознанного движка (Битрикс: /bitrix/, /local/, /upload/; WordPress: /wp-content/, /wp-includes/…), что в них и сколько запросов.
6. **Медиа** — где массово лежат картинки, видео, документы: папки находятся по запросам к медиафайлам (upload — частный случай), по типам и объёму.
7. **Служебные файлы по группам** — для роботов (robots.txt, sitemap), фиды и выгрузки, иконки и манифест, проверочные файлы; кто забирает, есть ли ошибки.
8. **Подгружаемые блоки** — сводка по группам (всплывающие формы, AJAX-блоки, панель админки); они не считаются просмотрами страниц.
9. **Параметры в адресах** — по группам: реклама, служебные поисковиков, фильтры каталога (ссылка на «Фильтры и поиск»), прочие.

Сотрудники и мониторинги переезжают на лист «Люди и боты». **Тематика:** движок описывает устройство нейтрально; смысл даёт Детектив по подсказкам из лога (слова адресов, рекламные фразы utm\_term, названия кампаний, имена форм), при наличии интернета — по заголовку главной, иначе — одним необязательным вопросом в анкете. В «О сайте» строка «Тематика» — только от Детектива или человека, с пометкой, откуда взято.

**Закрытые зоны — по поведению, не по названию.** Раздел с именем кабинета без входа и внутренних страниц — обычная страница (в «Простых разделах» с пометкой). Если движок показывает форму входа прямо на закрытой странице (Битрикс: ?login=yes, ответ размера отпечатка формы) — это не «открыто без входа». **Вход и регистрация — тоже конверсии:** в блоке «Формы, заявки и вход» — успешные и неудачные входы, регистрации и восстановление пароля, если они есть у людей (запросы сканеров к /signup, /register, /login с ответом 404 не считаются). В списках адресов — каждый адрес с новой строки.

**Числа во всех отчётах:** тысячи всегда отделяются пробелом (формат ячейки не зависит от языка Excel), десятичный знак в текстах — запятая. Уровни каталога подписываются «Ур. I: Индексная каталога», «Ур. II: Раздел — …», «Ур. III: Подразделы» (с названиями по строкам), «Ур. …: Элементы — …»; в колонке «Адреса» — «Шаблон:» и примеры, каждый с новой строки.

**Приложения к «Анатомии»** (сразу за ней, со ссылками под блоками): «Анатомия — отправки форм» (каждый адрес отправки, что это и почему заявка или нет), «— подгружаемые блоки» (доля запросов сразу после страницы), «— служебные файлы» (кто забирает, коды, размер), «— параметры» (каждый параметр и группа). Лист IP — в 04 Bots (в Overview только если блок Боты не выбран). Лист «GET-отправки» — в 03 Load\_Security, и он же — доказательство проблемы «Персональные данные в адресе (GET)» (тема «Безопасность»). Персональные данные определяются по значениям (телефон, почта, явные поля ФИО/телефона/почты), а не по имени параметра: name=‹название проекта› — не данные человека; зонды сканеров не считаются.

Порядок строк — естественный для данных (для событий — по времени). Плашка «Остальные» в «Проблемах» — #666666 с белым текстом.

**Точки приёма данных и POST-отправки.** В Overview перед «Конверсиями» — лист «Точки приёма данных»: только то, что сайт реально принимает (заявки, вход, фильтры и поиск через GET — по параметру кнопки или ключу поиска, одной строкой на раздел; служебные скрипты, админка, загрузка файлов; «Проверить» — обычная страница, отвечающая на POST). Колонки: Адрес · Метод · Что это · Почему так · Отправок · IP · Коды ответа · Первая · Последняя. В 03 Load\_Security — «POST-отправки» (пара к «GET-отправкам»): все адреса POST включая сканеры, строки сканеров тонированы, причина человеческим языком (404 — страницы нет, адрес WordPress на другом движке, отказ защиты). Что из него выделять — решим при разборе файла безопасности.

**Успех заявки (решение 3 октября).** Одной переадресации мало. Заявка засчитывается, если после отправки был ответ 302/303 **и** следующий запрос того же IP в пределах 10 секунд подтверждает успех: адрес с меткой успеха (success=, formresult=addok, «спасибо») или возврат на страницу формы. Неподтверждённые переадресации не засчитываются; форма без единого подтверждения помечается «Заявка?». В «Точках приёма данных» и «POST-отправках» колонки: Адрес · Метод · **Опознано как** · Отправок · **Уникальных IP** · **Улики** (с числами подтверждений) · Коды ответа · Первая · Последняя; сортировка — по числу отправок. В точки приёма входят и GET: фильтр, поиск, пагинация, тип отображения, сортировка (только люди, одна строка на раздел), и точки API/обмена (1С, REST, вебхуки — успешные ответы не от сканеров); чего нет — пишется «обращений не найдено».

**Полнота проверки (решение 2 октября).** Список искомого берётся из ТЗ, а не из логов одного сайта: движок не должен подстраиваться под один проект.

- **Реестр проверок.** Каждый тип проблемы из ТЗ связан с детектором и листом. В отчёте у каждого — одно состояние: найдено / проверено, не найдено / не применимо (нет рекламы, форм, error-лога) / детектора пока нет. У здорового сайта проблем нет, но видно, что всё проверено.
- **Сигналы без проблемы.** У аналитических листов задан признак проблемы (хотлинк свыше порога, макросы в метках, ошибки робота в одном шаблоне…). Сигнал есть, карточки нет — пункт попадает в brief.json для Детектива: завести проблему или отметить «норма, потому что…».
- **Пороги — относительные** (доли, сравнение с обычным для этого сайта), в файле правил. Сосредоточенные проблемы ищутся по шаблонам, а не только по сайту в целом.
- **Тесты (позже, когда движок устоится):** синтетические логи с подложенной проблемой каждого типа в разных окружениях (nginx/Apache, Битрикс/WordPress/статика, с рекламой и без) — найдена и с нужной важностью; **чистый лог** здорового сайта — ни одной проблемы (защита от выдуманного). Реальные логи — с нескольких непохожих сайтов; первый такой набор после АСПТ — следующий клиент, после того как отчёты доведены до конца.

## Справочники и самообучение

Знания о движках, сервисах и типовых решениях лежат в `data/reference/`, по файлу на сущность, в одном формате (описан в README там же). Новое добавляется файлом, без кода.

| Папка | Что | Когда применяется |
| --- | --- | --- |
| `common.json` | рекламные метки, параметры поисковиков, сброс кэша, файлы для роботов | всегда |
| `engines/` | движок: папки, закрытые зоны, адреса, параметры | только найденный на сайте движок |
| `services/` | коллтрекинг, метрики, рекламные виджеты, CRM, оплата | по ключам |
| `solutions/` | самописные решения студии | если найдены их признаки |
| `learned/` | найденное ИИ поиском + журнал `CHANGELOG.md` | всегда, ниже курированных |

**Порядок решения для параметра (поведение важнее имени: представиться ключ может кем угодно):** кто спрашивает (атака, подставной адрес, сканеры, ключ чужого движка без людей, без людей и почти одни ошибки, обращения к папке движка, которого на сайте нет, обращения в раздел, где людям и сотрудникам за весь период ни разу не ответили 2xx — зонд; переадресация успехом не считается) → справочник → дедукция. Дедукция — вывод по сочетанию улик: имя ключа + куда идут запросы (системные папки движка по справочнику, закрытый раздел сайта, обычные страницы, обработчик) + кто отправляет (люди со страниц сайта, сотрудники, только роботы) + какие ответы. Один и тот же `form` в обработчике от людей и в `404.php` от роботов — разные выводы. Улики пишутся в «Опознание». Ключи одного семейства (`itemsFilter_*`) решаются вместе и показываются одной строкой.

**Группы:** Реклама и аналитика · Поисковики и Яндекс · Данные форм (только справочник: стандартные поля движков и CRM) · Поиск и навигация · Служебные движка (справочник или системные папки движка; закрытые разделы, сделанные на сайте, — не движок) · Логика сайта (придумано программистом; пользуются люди со страниц сайта — от 20 визитов, или сотрудники в закрытом разделе; только дедукцией, в справочник и поиск не идёт) · Метки сервисов · Сброс кэша · Атаки и зонды · Неизвестные.

**Лист «Параметры запросов»:** Параметр · Группа · Запросов · Людей · Опознание · Основание · Значений · Частое значение · Точки обращения · Спутники.

Ссылок на источники на листе нет: они устаревают; кому нужно — проверит сам или перекрёстным поиском. Ссылки живут только в справочнике. Цвет строк: «Неизвестные» — серый EFEFEF, основание «Дедукция» — светло-серый F7F7F7, «Атаки и зонды» — персиковый.

**Пороги — в долях от размера лога.** Абсолютные числа ломаются на малопосещаемом сайте или коротком периоде. Порог = max(минимум, доля × база), база — визиты людей, запросы или IP; минимум (2–5) — только против одиночного шума. Для безопасности порогов нет: одна попытка инъекции — уже факт. Пороги лежат в `data/thresholds.json` и правятся без кода. Переведены: «Параметры запросов», «Файлы», «Динамические блоки». TODO: пройти остальные пороги движка (подготовка, блоки проблем, важность).

**«Динамические блоки»** (бывшее «Анатомия — подгружаемые блоки»), сразу за «Анатомией сайта»: Блок · Размер, КБ · Вид · Загрузка (авто / по действию) · Запросов · Визиты (люди) · Автозагрузка, % (доля запросов в первые 3 с после страницы в том же визите) · Охват страниц (сколько страниц вызывают блок) · Коды ответа · Первый · Последний. Каждый блок — отдельной строкой; перезагрузки списка по фильтру — одной строкой (это навигация, подробно на «Фасетах»). Ошибки (4xx/5xx без 499 от 1% или хотя бы один 5xx) — персиковым, неопознанные — серым.

**Коды ответа.** На листах больших таблиц — две колонки: «Ответы» (2xx, 3xx, 499) и «Ошибки» (4xx/5xx, кроме 499 — человек ушёл сам). Ошибки — красным #C00000 везде, включая смешанные списки кодов на других листах. Строки с ошибками не заливаются: много это или мало, решает аналитик; в «Проблемы» — только если доля высокая. Визиты людей — «Визиты (люди)», разные IP людей — «IP (люди)»: людей по логу не посчитать.

**«Страницы»** (бывший TOP500, вместо «Спроса»; в подзаголовке — «TOP500 — самые посещаемые страницы сайта»): 500 самых посещаемых живых страниц из реестра адресов (людям или своим отвечали 2xx; зонды и конструкты не входят), без деления на каталоги и ленты, по визитам людей. Колонки: Страница · Просмотров · Визиты (люди) · IP (люди) · Заявок отправлено · Ответы · Ошибки · каналы визита: Реклама, Поиск, Прямые заходы, Карты, Ссылки с сайтов, Внутренние переходы, Прочие. Динамики нет.

**«Разделы»** — запрашиваемые разделы сайта (первый уровень адреса, срез реестра без зондов): Раздел · Статус (существует / переадресация / сломан / не существует — людям ни разу не ответили 2xx, строка персиковая) · Страниц · Существует · Просмотров · Визиты (люди) · IP (люди) · Заявок отправлено · Ответы · Ошибки · каналы как в «Страницах». Динамики нет.

**«Типы страниц»** — страницы одного вида, собранные по шаблону адреса (`/projects/*/flat/dom-*/s*/e*/n*/`); тип показывается, только если в нём два адреса и больше; колонки как в «Страницах», плюс число страниц и пример. Нужен, чтобы видеть интерес и ошибки по виду страниц (карточки квартир, новости), а не по одной странице.

**Зонды и сигнатуры сканеров** — `data/reference/probes.json`, один список для реестра адресов, визитов и блока безопасности. Зонды ищутся и в адресе как есть, и в раскодированном (`/.%65%6e%76` — это `/.env`). Однозначные: секреты и конфиги (в том числе .htaccess, .gitignore, .settings.php, dbconn.php, terraform), дампы, отладка, панели БД, IoT, WordPress на чужом движке, обход фильтров (буквы и цифры в %-кодах). Неоднозначные: установщики, архивы, типовые админки, поиск контактов (на разных языках), поиск входа, кабинета и корзины. Сигнатуры визита «сканер под браузер» → «Боты»: однозначный зонд (одного достаточно); перебор неоднозначных зондов, которых на сайте нет (от 3, в визите или с одного IP; настоящие страницы, открытые заодно, не оправдывают); перебор вариантов одного файла (от 3); веер 404 (от 5 разных страниц, в визите или с одного IP). **Общий критерий для всех сигнатур:** считаются только адреса, которые обращающийся выбрал сам; ресурсы и ссылки, которые браузер взял со страниц сайта, — ошибки сайта, а не перебор (реферер «сам на себя» — подделка, не в счёт).

## Общие критерии: адрес и тот, кто обращается (утверждено, реализовано 4 октября)

Листы не держат своих условий «что такое страница / файл / раздел / бот»: есть две общие классификации, листы фильтруют их результат. Правила и веса — в справочниках, самообучаемые (как параметры: незнакомое — в brief, Детектив ищет и пишет в learned).

**1. Реестр адресов.** Каждый запрошенный адрес — три оценки:

- форма (по виду): страница (без расширения или с расширением страниц; хвост-домен — тоже страница), файл (расширение из справочника расширений с группой — тот же, по которому группируются «Файлы»; незнакомое расширение — в самообучение), конструкт (шаблон JavaScript — ${…}, {{…}}, ' + href +; параметры без ?; пробелы, кавычки, двойные слэши, мусорная кодировка). Раздел — уровень страницы, не форма.
- существование (по ответам): живой (людям 2xx), переадресация, не существует (только 4xx), сломан (5xx).
- смысл (по справочникам): зонд и какой, служебное движка, файл для роботов, обычное.

Реестр — `engine/nxld/classify.py`, справочник расширений — `data/reference/extensions.json` (страничные расширения, домены в хвосте, правила по адресу, 13 групп файлов, около 180 расширений). Пробел (`%20`) в адресе законен («дом 1» в фильтре), абсолютная форма запроса (`GET http://сайт/путь`) — тоже. Незнакомые расширения (не зонды и не несуществующие) — в brief «незнакомые\_расширения»; Детектив пишет их в edits.json → «расширения» со ссылкой, они сразу переходят в группу и сохраняются в `learned/extensions.json`.

Срезы: «Разделы» — страницы первого уровня; «Типы страниц» и «Страницы» — живые страницы; «Файлы» — файлы, кроме зондов; зонды — в безопасность; конструкты — лист «Конструкты в адресах» в 03 (вывод: битый код страницы / битая ссылка снаружи / роботы / посторонние — инъекция или зонд), а собранные скриптами сайта у людей — ещё и лист «Битые адреса из скриптов» с карточкой в 02. Утечка служебного файла — только для однозначных зондов и тех неоднозначных, которые люди и свои не получают как обычный адрес.

**2. Кто обращается — по виду и поведению, через улики с весами.** Вид: User-Agent, сеть (домашняя / хостинг / VPN), страна, подделка. Поведение: загрузка ресурсов, темп и паузы, глубина, доля 4xx, зонды, перебор вариантов, откуда пришёл, повторяемость (дни, визиты). Выводы: человек-посетитель; человек ошибся адресом (остаётся человеком); свой; робот честный; бот-маскировщик; сканер; человек-исследователь (живой темп, ресурсы, но зонды — хакер или разработчик): разово — исключается из людей-клиентов без предупреждения; регулярно — карточка «Человек систематически исследует сайт». Поиск входа по чужому адресу (/login на сайте с известным входом) — улика «не свой».

**3. Кто обращается — как сделано.** Улики и веса — `data/reference/actors.json`. Подозрение доказывают сигнатуры зондов; дальше решается, автомат это или человек. Баллы человечности: браузер отрисовал страницу (от 3 ресурсов с реферером-страницей сайта) — 2; живой темп (меньше запроса в секунду) — 2; не хостинг и не VPN — 1; настоящий браузер — 1; ходит по живым страницам — 1; человек — от 5 баллов. Автомат без баллов: хостинг; больше 3 разных браузеров с одного IP (ротация User-Agent); зонды чаще раза в 3 секунды; больше 10 зондов; половину его зондов просили ещё больше 3 подозрительных IP (словарь программы, распределённый скан). Человек-исследователь разово — исключается из людей молча; регулярно (подозрительные визиты в 2 дня и больше) — лист «Исследователи сайта» и карточка «Человек систематически исследует сайт». На АСПТ после всех улик живых исследователей не осталось: все кандидаты оказались сканерами с ротацией браузера или общим словарём.

Отчёт сразу показывает «найдено поиском» со ссылкой, запись сохраняется в `learned/`. Совпало с поведением на другом сайте — подтверждение; спорит — конфликт, на листе побеждает поведение; конфликтов больше подтверждений — запись опускается и ищется заново. Записи из поиска старше 180 дней перепроверяются, когда ключ встречается снова. Сайт в справочнике — отпечатком (`сайт-xxxxxxxx`), не адресом: справочник уходит в общий репозиторий.

**Листы Overview, связанные со справочником:** «Параметры запросов» (Параметр · Группа · Что это · Откуда знаем · Запросов · Людей · Значений · Частое значение · Где · Приходит вместе с; стоит перед «Фасетами», за «Точками приёма данных»), «Файлы» (все файлы, кроме страниц: свёрнуты по папке и виду, источник — со страниц сайта, напрямую, другие сайты; браузеры и роботы) и «Логи» — в конце, перед снимком.

**Важность «Замечание»** — четвёртая, ниже «Остальных», серая плашка: не проблема, решает аналитик (первое — нет файлов для ИИ-поиска: llms.txt, ai.txt).

### 16.2. Индексная таблица (`NXLD_01_Overview.xlsx`, первый лист)

Индекс лёгкий: проблемы целиком на втором листе «Проблемы», формы и каталог — на листе «Устройство сайта» (с расшифровкой, что какому шаблону соответствует), выводы очистки по каналам — в Маркетинг.

1. **Шапка:** логотип, «NX Log Detective — сайт …», плашка «Первичная проверка» или «Повторная: сравнение с проверкой за …», дата отчёта, версия.
2. **Проверка:** сайт и другие хосты в логах, период и число дней, исходные данные (строки access и error, число файлов).
3. **Условия проверки** — только непустые строки: непроверенные блоки, база сравнения, присланные IP, отметки и правила, проверки в интернете, пробелы в данных. Строк «не выполнялись / не загружались / —» нет; если ничего особенного — «Проверены все блоки, данные полные».
4. **Что за сайт** (отдельный блок; только то, что видно по логу, — отрасль и B2B/B2C не определяем): **назначение** — лендинг / сайт компании / каталог с заявками / интернет-магазин / контентный сайт / портал или сообщество / закрытая платформа (кабинет) / веб-сервис или API; **размер** по числу разных страниц, отданных людям с ответом 200 — маленький (до 50) / средний (до 5 000) / большой; **аудитория** — публичный / закрытый / смешанный. Под строкой — по чему определено (корзина, формы, доля карточек, доля визитов после входа, доля API). Тип определяет движок, Детектив может поправить. Тип влияет на реестр проверок (что не применимо) и на важность: у лендинга ошибка на главной — всегда важная; у закрытой платформы форма входа и закрытые разделы — норма, реклама и поиск почти не применимы, важнее подбор паролей и ошибки после входа.
5. **Технологии:** сервер по путям (правила в файле настроек и дополняются: `/mnt/data/www/<проект>` — своя виртуальная машина; `/var/www/<пользователь>/data/www/<сайт>` — панель ISPmanager, вероятно общий хостинг; иначе — путь и «тип хостинга по логам не определён»); ОС (Linux/Unix по путям, дистрибутив по логам не виден); веб-сервер, PHP-FPM, протокол; движок; адрес админки.
6. **Трафик и заявки:** визиты людей, роботов, ботов, своих с долями; просмотры людей; визиты во встроенных браузерах; заявки (отправлено, принято от людей, от ботов, тесты, конверсия). Под ними — фраза «Как считали»: цифры после очистки, потому меньше сырых и ближе к Метрике.
7. **Проблемы** — одна строка-ссылка со счётчиком по важности.
8. **Содержимое документа: таблица «Лист — Что на нём» по всем листам файла, включая сам обзор, со ссылками. Затем отдельный блок «Структура отчёта»: таблица «Файл — Что в нём» по всем файлам архива (Excel по блокам, текст для Redmine, снимок). Блок «Проблемы» — маленькая таблица «Срочно / Важно / К сведению / Где смотреть» с цветами важности. Таблицы — как в фирменном образце: оранжевая шапка с белым жирным текстом (крупнее строк), тонкая сетка, отступ текста от линий, числа справа на светло-сером; в карточках — тонкий разделитель строк; сетка листа включена**.

Оформление по фирменному образцу: заголовок Montserrat 16 жирный оранжевый, подзаголовок Comfortaa серый, блоки-карточки с заливкой #EFEFEF, пояснения — #FCE5CD, акцентная плашка — заливка #F57041 с белым текстом. Индекс — образец для первых листов всех файлов; образец табличных листов — второй лист «Проблемы».

Технические данные (файлы логов, сервер, движок, карта сайта, очистка) — **только в общем файле**, отдельным листом в конце. В файлах блоков — только короткая карточка проекта (сайт, период, блок) и ссылка на общий файл.

### 16.3. Структура файлов: важное впереди

- Листы группируются по смыслу: «Проблемы» → листы-списки на исправление (что именно править) → аналитика → справочные и технические листы в конце. Группы видны по цвету ярлыков и в содержании.
- Мелкие листы одной темы объединяются; пустые листы не создаются.
- Внутри таблицы строки идут от важного к неважному; служебные столбцы — в конце или скрыты.
- У каждого листа — заголовок и одна строка «что это за таблица и как ей пользоваться».

### 16.4. Вёрстка таблиц

- **Названия столбцов — человеческие**, без подчёркиваний и сокращений, единицы в скобках: «Ушли сразу, %» вместо «мгновенный\_уход\_%». Все названия — из одного словаря, одинаковые во всех файлах.
- Таблицы не разъезжаются: ширины столбцов по типу данных, перенос длинного текста, высота строк по содержимому, закреплённая шапка и фильтры.
- Форматы чисел: разделители тысяч, проценты как проценты, даты и время в одном виде, объёмы в МБ/ГБ.
- Для печати: альбомная ориентация, по ширине страницы.
- Вид файлов проверяется глазами один раз на каждую версию на контрольных данных (не на каждом прогоне — раздел 15).

### 16.5. Проблемы: прозрачно и готово к исправлению

Каждая проблема должна читаться без захода в другие листы и вести к исправлению:

**Вид листа «Проблемы» (решение 2 октября).** Лёгкие карточки в стиле индекса. Градации для читателя везде (Excel, индекс, Redmine): **Приоритетные · Важные · Остальные**; слова «срочно» нет, маркер в рекомендациях — «В первую очередь». Каждый раздел открывает плашка в стиле «Первичная проверка» с числом и разбивкой по темам: приоритетные — оранжевая с белым текстом, важные — персиковая #FCE5CD, остальные — серая #CCCCCC (как в фирменном образце). Блок не упоминается — вместо него **тема**: Заявки, Реклама, Сайт, Сервер, Безопасность, Нагрузка, Поиск. Карточка: заголовок (номер и суть человеческим языком; оранжевый, с оранжевой линией, тема и статус — справа) → **Из показаний** (цифра в контексте, когда, продолжается ли) → **Что делать** (и где) → **Признак устранения** (по какому признаку в логе видно, что проблема устранена) → «Расследование и улики» со строками второго уровня (Основание — почему это проблема; Обстоятельства — что подняло или опустило важность, если есть; Доказательство — пример из лога у каждой проблемы) → ссылка «Подробно: лист … →». Остальные — такие же карточки, короче: без признака устранения и расследования. Заголовок и показания собирает движок по шаблонам типов проблем (читаемо и без ИИ), ИИ может улучшить через edits.json. Плоская таблица с фильтрами — в отчёте по ошибкам.

**Статусы при повторной проверке** (метка справа в заголовке карточки; порог 30% в настройках): новая; стала хуже (главная цифра +30% и больше); сохраняется; исправлена частично (−30% и больше, но ещё есть); исправлена (раздел в конце, с оговоркой, если не было запросов); отмечена как норма (раздел в конце). При первичной проверке меток нет.

- **Точное название объекта.** Не «площадки», а «сторонние мобильные приложения в РСЯ»; разные типы объектов — разные проблемы (приложения, сайты РСЯ, сервисы Яндекса отдельно).
- **В цифрах и в контексте:** сколько, какая доля от целого, за какой период, с чем сравниваем (например, с поиском).
- **Доказательство:** конкретный пример — адрес, время, IP или запрос, по которому проблему можно воспроизвести или найти.
- **Как найдено:** критерий одной фразой («больше 30 визитов и ни одной заявки»).
- **Что сделать — по шагам** и где именно (кабинет, раздел, файл конфига). Если нужен список (площадки к исключению, битые ссылки, редиректы) — отдельный лист в готовом для вставки виде и ссылка на него.
- **Как проверить, что исправлено.**
- Важное не тонет в деталях: проблемы по важности, формулировка в одну строку, подробности — в соседних столбцах; однотипные мелкие проблемы склеиваются, крупные не смешиваются.
