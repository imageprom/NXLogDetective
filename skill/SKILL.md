# NX Log Detective 0.2.0-alpha

Пиши бренд так: **NX Log Detective**, кратко **NXLD**. NX — всегда заглавными. В именах папок и файлов — без пробелов (`NXLogDetective`, `NXLD_…`).

Принцип: **код измеряет, ИИ расследует**. Всё, что можно посчитать, считает движок `engine/nxld_run.py`. Твоя работа — анкета, проверка карты сайта, расследование странного, формулировки проблем и выдача результата. Состояния между сессиями нет: всё нужное приходит на вход, всё полученное уходит на выход.

## 0. Подготовка

1. **Скопируй скилл в рабочую папку** — папка скиллов только для чтения, а движок дописывает справочник (самообучение):
   ```bash
   cp -r <папка этого SKILL.md> ./nxld && cd ./nxld
   ```
   В установленном скилле движок и базы лежат рядом с SKILL.md (`engine/`, `data/`); в репозитории — на уровень выше (`../engine/`, `../data/`). Все команды ниже — из этой копии. Нужны только Python 3, pandas, numpy, openpyxl. Интернет не нужен: база IP → сеть лежит в `data/`.
2. **Проверь обновления** одной командой: `python3 tools/check_update.py`. Она только сообщает: если есть версия новее — скажи человеку одной строкой («вышла 0.2.1, обновите скилл: архив в папке releases/ на GitHub»). Нет сети — работай дальше молча. Сама ничего не обновляет.
3. Рабочая папка — любая (`./work`). Результат — `./out`. Логи из чата лежат в папке загрузок — передавай их путями, не копируя.

## 1. Анкета (одним вопросом, ответ можно не ждать)

- **Блоки:** ☑ Общий анализ и ☑ Ошибки — всегда; ☐ Нагрузка и безопасность; ☐ Боты; ☐ Маркетинг; ☐ SEO.
- **Действие:** ◉ Полная проверка / ○ Сравнение (база: снимок `.snapshot.json`, старые логи или анализ в этом же чате).
- **Сигнатуры и правила** — выгружаются всегда одним пакетом STIX 2.1 (раздел 7); остальные форматы — позже.
- **Дополнительно:** список подозрительных IP; отметки «это норма».
- **Адреса для проверки из сети** — после расчёта (раздел 4). Открыть страницу сайта можно только по адресу, который человек прислал сам. Поэтому Детектив собирает список (robots.txt, карта сайта, главная, утёкшие файлы из `brief.проверки_из_сети`) и просит прислать его одним сообщением. Человек может прислать и содержимое файлов — текстом или вложением, это тоже проверка.

Если ответа нет — полная проверка по всем блокам.

## 2. Приём и разведка

```bash
python3 engine/nxld_run.py --logs <файлы и папки> --work ./work --stage prepare
```

Читает `.log`, `.gz`, `.zip`, папки; сам определяет access/error, сайт, формат, удаляет дубли на стыках файлов. На 10 млн строк — 2–3 минуты. Если файлы большие и передача рвётся — попроси части до 50 МБ.

Сразу покажи человеку первым экраном **«Что на входе»** из `work/inventory.json` и `work/site_map.json`:
- файлы и типы, сайты, период, число строк, пропуски, дубли;
- сервер (nginx/Apache, PHP-FPM), движок или «статический HTML», адрес админки;
- цели (формы) и признак успеха, элементы каталога, подгружаемые блоки, рекламные метки, сотрудники, мониторинги.

Проверь карту глазами. Если что-то не так (лишний домен, не та цель, свой IP) — запиши поправки в `map_override.json` (`site_hosts`, `staff_ips`, `catalog_templates`) и перезапусти prepare с `--map-override`. Неприменимое (нет форм, нет рекламы) не придумывай — так и пиши.

## 3. Расчёт блоков

```bash
python3 engine/nxld_run.py --work ./work --out ./out --stage analyze \
   --blocks overview,errors,load,bots,marketing,seo \
   [--check-ips 1.2.3.4,5.6.7.8] \
   [--prev прошлый.snapshot.json] [--marks отметки.json]
```

Движок считает листы и черновые проблемы (`work/results.pkl`). Сравнение включается параметром `--prev`. Отметки «это норма» берутся из прошлого снимка автоматически.

## 4. Расследование (твоя часть)

Движок положил выжимку `work/brief.json`: проверка, портрет сайта, проблемы с важностью, материал по блокам, файлы и листы, открытые вопросы. **Начинай с неё, а не с таблиц.** Для точечных вопросов загрузи таблицы:

```python
import pandas as pd
R = pd.read_pickle('work/R.pkl')   # все запросы: ts, ip, method, base, query, status, bytes, ref, ua, fam, vid, is_page, tpl, goal ...
V = pd.read_pickle('work/V.pkl')   # визиты: group, subgroup, channel, entry, n_pages, n_static, n_goal, n_conv ...
```

Что делать:
- проверь каждую приоритетную проблему (`Срочно` в данных): правда ли это или артефакт (заглушка вместо файла, свой тест, мониторинг). Если первое подозрение не подтвердилось, это тоже вывод для текста;
- проверь `что_за_сайт` (назначение, размер, аудитория): если движок ошибся — поправь через `site_profile` в `edits.json`;
- разбери `сигналы_без_проблемы` из brief: признак проблемы на листе есть, а карточки нет. По каждому — завести проблему в `edits.json` или написать в тексте, почему это норма. `покрытие` показывает, что проверено и не найдено, что неприменимо и для чего детектора пока нет — неприменимое и непроверяемое не выдумывай;
- найди то, что правила не ловят: даты изменений, связи между IP, смысл листов «Изменения статусов», «Операторы»;
- неопознанных роботов и мониторинги не угадывай: «не опознан — на усмотрение оптимизатора»;
- телефоны и почты в отчётах только маскированные;
- разбери `незнакомые_параметры` из brief (ниже, «Незнакомые параметры»);
- рамки: сначала приоритетные и странное, до 10–15 уточняющих запросов, вывод команд короткий.

### Незнакомые параметры: найти и записать в справочник

Справочник (`data/reference/`, формат — в его README) знает параметры движков, сервисов и типовых решений. Чего в нём нет, движок определил **дедукцией** — по сочетанию улик (имя ключа, куда идут запросы, кто отправляет, какие ответы; улики видны в колонке «Опознание») — либо оставил в «Неизвестных». Это и есть `незнакомые_параметры`: ключ, сколько запросов, частые значения, где встречается, кто запрашивает, с какими ключами приходит пачкой, и `есть_у_другого_движка` — если ключ описан у движка, которого на сайте нет (часто это зонды под чужой движок).

Что делать с каждым, начиная с частых:
- найди в сети, что это: документация движка или сервиса, справка, сборники (списки для Clean-param, статьи разработчиков). Поисковики и сервисы плодят новые метки — не угадывай по имени;
- **нашёл источник** — запиши в `edits.json` → `справочник`: ключ (или шаблон семейства с `*`), группа, что это, ссылка. Без ссылки запись не примется;
- **не нашёл** — не пиши ничего: ключ останется с группой по дедукции, это честно;
- «Логика сайта» (придумано программистом сайта, ими пользуются люди или сотрудники) и служебные параметры движка, которыми пользуются только свои, в brief не попадают: в сети этого не найти, в справочник не пиши;
- зонд под известную уязвимость (CVE, exploit-db, публикация исследователей) — тоже пиши, группа `Атаки и зонды`, ссылка на публикацию;
- `по: поиск, устарело` — запись из поиска старше полугода: перепроверь тем же способом.

Группы: `Реклама и аналитика`, `Поисковики и Яндекс`, `Данные форм`, `Поиск и навигация`, `Служебные движка`, `Метки сервисов`, `Сброс кэша`, `Атаки и зонды`. Основание на листе: «Документация», «Сообщество», «Оперативный поиск» (это твоя запись), «Дедукция».

Найденное сразу попадает на лист «Параметры запросов» с основанием «Оперативный поиск» и ссылкой, и сохраняется в `data/reference/learned/params.json` для следующих анализов — подтверждать никому не нужно. Справочник сам поднимает запись, когда её подтвердят другие сайты, и опускает, когда она спорит с поведением; всё пишется в `learned/CHANGELOG.md`.

### Незнакомые расширения: то же самое для файлов

Вид файла движок берёт из справочника расширений (`data/reference/extensions.json`). Чего там нет, лежит на листе «Файлы» в группе «Неизвестный вид» и приходит в brief как `незнакомые_расширения`: расширение, сколько запросов и адресов, примеры. Зонды и файлы, которых на сайте нет, туда не попадают — это не словарь, а атаки и опечатки.

Найди, что это за формат, и запиши в `edits.json` → `расширения`: расширение, группа (одна из групп справочника: «Картинки», «Документы», «Данные для виджетов» и т. д.), что это, ссылка. Без ссылки запись не примется. Найденное сразу переносит файлы в группу и сохраняется в `data/reference/learned/extensions.json`.

### Незнакомые системы мониторинга

Системы мониторинга движок узнаёт по справочнику (`data/reference/monitors.json`) и проверяет поведением: мало адресов через равные промежутки. Чего в справочнике нет, приходит в brief как `незнакомые_мониторинги` (имя, User-Agent, IP, визиты). Найди сервис и запиши в `edits.json` → `мониторинги`: сервис, шаблон для User-Agent, ссылка. Без ссылки не примется. Неопознанный мониторинг без имени (по ритму, под видом браузера) не угадывай — на него заводится карточка, решает аналитик.

### Регионы рекламы: справочник

Код региона из рекламной метки движок расшифровывает по `data/reference/regions_yandex.json` (геобаза Яндекса и вложенность регионов Директа). Неизвестный код остаётся кодом — это нормально, отдельно об этом не пишется. В brief (`маркетинг.регионы`) — дата справочника и доля кликов без названия. Если справочнику больше 90 дней **или** без названия больше 10% кликов — одна строка в «Открытых вопросах»: «справочник регионов пора обновить: `tools/fetch_yandex_regions.py` с токеном Директа». Сам в API не ходи: токена у тебя нет и не должно быть.

### robots.txt и карта сайта: проверить из сети

Запиши результат в `edits.json` → `проверка_сайта`: `{"/robots.txt": {"итог": "отвечает", "когда": "…", "что": "…"}, "/sitemap.xml": {"итог": "404", "когда": "…"}}`.

Если интернет есть, открой `robots.txt` и адрес карты сайта из него (или `/sitemap.xml`) одним запросом каждый. Сверь с листом «Файлы для роботов» (NXLD_06_SEO.xlsx, `brief.seo.файлы_для_роботов`): если по логу карта сайта не отвечала, а сейчас отвечает — в тексте «по логу не отвечала, на <дата проверки> отвечает». Запреты в robots.txt, которые объясняют «Страницы без обхода» или паразитные адреса (Disallow, Clean-param), назови в тексте. Без интернета — «не проверено».

### Утечки и внешнее встраивание: проверить из сети

Если интернет есть, открой каждый файл из `brief.проверки_из_сети.утечки` (адреса — из сообщения человека, см. анкету) (в Excel — NXLD_03_Load_Security.xlsx, лист «Служебные данные») и запиши в `edits.json` → `проверка_утечек`: `итог` — «открыт» или «закрыт», `когда` — дата и время проверки, `внутри` — **только признаки** («пароль базы: есть», «ключи API: нет»), сами секреты никогда не переписывай. «открыт» оставляет «Тревогу» и в тексте пишется «проверено из сети <когда>: открыт»; «закрыт» снимает «Тревогу». **«Тревога» — только если внутри существенное**: пароли, ключи, доступ к базе — `"тревога": true`. Открыт, но секретов нет (`"тревога": false`) — проблема остаётся приоритетной, файл всё равно закрыть: он показывает, как устроен сервер. Без проверки «Тревога» стоит по логу, в тексте — «по логу, на конец лога». Дела в 04 пересчитываются так же. Почти пустой ответ (десятки байт) обычно значит, что PHP выполнился, а исходник не отдан, — так и напиши.

Для сайтов из `brief.проверки_из_сети.встраивание` (в Excel — NXLD_03_Load_Security.xlsx, лист «Файловый трафик») сверь IP их домена с IP нашего сайта (DNS-запросом). Если DNS-запросов в среде нет (облачная песочница без сети в оболочке) — не выдумывай: вывод остаётся по логу, в «Открытых вопросах» — «встраивание не сверено по DNS». Совпадает — `"лежит на нашем сервере"`, нет — `"чужой сайт"`; запиши в `edits.json` → `встраивание`.

```json
{"проверка_утечек": {"/.htaccess": {"итог": "открыт", "когда": "06.10.2026", "внутри": "правила переадресации; паролей нет", "тревога": false}},
 "встраивание": {"aspt-development.ru": "лежит на нашем сервере"}}
```

Правки проблем запиши в `edits.json` — они попадут в Excel:

```json
{"add": [{"блок": "Маркетинг", "важность": "Важно", "что_происходит": "…", "факты": "…", "где_править": "…", "что_сделать": "…", "главная_цифра": 0, "лист": "…"}],
 "remove": ["ключ ложной проблемы"],
 "update": {"ключ": {"важность": "К сведению", "факты": "…"}},
 "site_profile": {"назначение": "Закрытая платформа (кабинет)", "признаки": ["…"]},
 "справочник": [{"ключ": "yhid", "группа": "Поисковики и Яндекс", "что": "…", "ссылка": "https://…"}],
 "расширения": [{"расширение": "glb", "группа": "3D и графика", "что": "…", "ссылка": "https://…"}],
 "мониторинги": [{"сервис": "Overseer", "шаблон": "Overseer", "ссылка": "https://…"}]}
```

## 7. Сигнатуры и правила: выгрузка STIX 2.1

Сигнатуры и правила защиты делаются по ТЗ, раздел 10. Паттерны **строятся** из данных проекта: гипотезы → признаки → пороги → проверка на логах. Выгрузка бывает двух видов:
- **полный пакет STIX 2.1** — для обмена между людьми со скилом, без потерь;
- **частичные форматы** — в одну сторону:
  - сигнатуры: Sigma 2.1.0 (YAML и JSON), EQL;
  - правила защиты: nginx, fail2ban, ModSecurity/Coraza, Yandex Smart Web Security, AWS WAF, Cloudflare;
  - списки IP и CSV.

В 0.2 выгружается полный пакет **STIX 2.1** (`engine/nxld/stix.py`, файл `*.stix.json` в архиве): сигнатуры (каждая — правилом Sigma целиком и шаблоном STIX), дела «Тревога», «Срочно», «Важно» со своими IP и сетями, улики между адресами, сколько раз видели, статус и уверенность, срок действия. Белого списка (сотрудники, сервер, мониторинги, подлинные роботы) и IP людей в пакете нет. Коды объектов — UUID v5 от наших кодов (SIG-…, номер дела): повторная выгрузка не задваивает объекты. Сигнатуры дел «К сведению» без адресов в пакет не попадают — их поведение Sigma не выражает. Пакет проверяется официальным валидатором (`stix2-validator`), если он установлен.

В тексте для Redmine STIX упоминается одной фразой в разделе «Файлы»: что это (открытый стандарт OASIS для обмена данными об угрозах, принимают OpenCTI, MISP и другие) и сколько в нём сигнатур, дел и IP (`brief.выгрузка_stix`). Остальные форматы (Sigma отдельными файлами, EQL, nginx, fail2ban, ModSecurity, SWS, AWS WAF, Cloudflare, списки IP) — позже. Прежний ручной формат `botsig/1` лежит в `signatures/legacy/` только для справки.

Если пользователь прислал свои правила (Sigma, STIX, список IP и т. п.), это **проверка логов по чужим правилам**, а не импорт. Скажи, что полноценная поддержка будет позже, и при необходимости проверь вручную по `R.pkl`.

## 8. Интернет (только если есть и только по делу)

Всегда: robots.txt и карта сайта (раздел 4), заголовки главной (одним запросом). По поводу из лога: утечки и встраивание (раздел 4), проблемный фид, перепроверка адресов из «Тревоги» и «Срочно» (до 10–20). Что проверено и когда — в `edits.json` и в тексте; без интернета — «не проверено», а выводы «сейчас» пишутся как «по логу, на конец лога».
